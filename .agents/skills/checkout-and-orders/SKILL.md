**How to edit this file:** one fact per line, as a list item under the heading it belongs to. Add a new rule as its own line, or a new `##` heading for a new topic. ## Delete Order

- **Delete Order (<KEY>-194)**: `deleteOrder({ orderId })` (`europe-west3`, admin only; `functions/src/orders/delete-order.fn.ts`, rule in `order-delete.ts`) deletes a **Cancelled** or **Payment Failed** order and its `orderStaffNotes` in one transaction and writes `auditLogs` (`action: 'order.delete'`); any other status answers `failed-precondition` "Only Cancelled or Payment Failed orders can be deleted. Cancel the order first." `syncOrderView` removes the guest view; `orderEmails` records stay. The Orders list row and `/admin/orders/:id` show **Delete Order** (asks first) to admins only, on those two statuses.
- A Payment Failed **Card** order can be deleted only 90 minutes after it was placed (`paymobFailedDeleteBlockedReason()`, Paymob intention expiry plus 30 minutes), because the shopper can still retry and `paymobWebhook` would confirm a late capture; sooner answers "The customer can still retry this card payment. Try deleting it again in an hour or two."

## Guest checkout (server)

- **Guest checkout (server, <KEY>-169)**: `createCodOrder`, `createInstapayOrder` and `createPaymobOrder` also accept a call with no sign-in that sends `guest: { email }` (valibot `GuestCheckoutSchema` in `order-request.ts`: trimmed, lower-cased, valid email); `identifyOrderCustomer()` in `functions/src/orders/order-customer.ts` decides who is ordering.
- A signed-in order call works as before (`requireRole` + `requireAcceptedTerms`) and ignores any `guest` block; `requireAppCheck` runs for guests too; no sign-in and no valid `guest` block is refused with `unauthenticated` "Enter your email to place your order."
- A guest agrees to the terms by placing the order (no tick box): the order saves `guest: { termsVersion, termsAcceptedAt }` (server time, `CURRENT_TERMS_VERSION` in `functions/src/auth/accepted-terms.ts`, keep equal to the Angular copy in `user-profile.model.ts`).
- Guest orders are priced with `signedIn = false`, so signed-in-only offers and offers with a once-per-customer limit (`limits.perCustomer`) never apply to them; every other offer applies as for signed-in shoppers.

## Order views for guests

- `orderViews/{viewKey}` is a public read-by-key copy of each guest order (`allow get: if true`; list and every client write denied, admins included). The `syncOrderView` trigger (`functions/src/orders/order-view.trigger.ts`, `europe-west3`) writes it on every write of an order that has a `viewKey` (it re-reads the order in a transaction, so out-of-order events never leave an old status; `retry: true`), with only the fields the order page reads (`orderViewFields()` in `order-view.ts`: status, payment method, pricing, shipping address, Paymob amount and `paidAt`, dates including `shippedAt` / `deliveredAt`, `deliveryFeeSetAt`, `needsReview`; never `cancelReason` or `statusHistory`), never staff-only fields, the email, the uid or the key; a deleted order deletes its view.

## Bag and checkout payments

- **Checkout payments (InstaPay + Paymob + Egypt COD)**: `CartService` keeps a guest's bag in `localStorage` (`atteya-cart-v1`) and a signed-in shopper's bag in `carts/{uid}` (`lines` of product id, variant id, choices and quantity, plus `updatedAt`; never prices), kept live with `onSnapshot` so it follows them across tabs and devices. It waits for `AuthService.isAuthReady()` before choosing (meanwhile it shows the guest bag, which is empty for a signed-in shopper after their first merge). On sign-in the guest bag is taken out of `localStorage` and added to the account bag in a transaction (same product and choices → quantities added, capped at 20; at most 20 lines; pure helpers `addCartLine` / `mergeCartLines` in `cart.model.ts`, tested by `npm run test:cart`); a failed merge puts the items back on the device for the next page load. Sign-out empties this browser's bag and leaves the account bag saved; a different account never sees the previous one's items. Changes made before the account bag's first snapshot are queued and applied to it. `ready` / `waitUntilReady()` say when the current person's bag has loaded (checkout waits for it before sending an empty bag home), and `clear()` (after Place Order) resolves when the account bag is saved or after 3 seconds, so the Paymob redirect does not drop it. Rules: only the owner reads or writes `carts/{uid}` (no delete, admins get no access); each write is checked line by line (at most 20 lines, the same limit as the order callables, quantity 1–20, at most 10 choices, no other fields) and `updatedAt == request.time`. Shoppers use `/checkout` and `/checkout/confirmation/:orderId` (client-rendered), signed in or as a guest (see the guest checkout lines below). Payment methods: **InstaPay** (Egypt only, listed first and preselected: the shopper transfers the full total, sends the screenshot on WhatsApp, and staff confirm), **Paymob** (card/wallet via Intention API → Unified Checkout; the only method outside Egypt; shown as "Coming soon" and refused while `STORE_INFO.payments.cardOrWallet` is `'coming-soon'`, see Store info) and **cash on delivery** (Egypt only; shipping fee by InstaPay first). Abroad checkout always uses Paymob. Egypt orders need a WhatsApp-reachable mobile (`isEgyptMobile()`, checked on the client and in `order-request.ts`). `createPaymobOrder` / `createCodOrder` / `createInstapayOrder` (`europe-west3`; the last two share `createManualOrder` in `create-manual-order.fn.ts` and `order-rate-limit.ts`; InstaPay fulfilment is `domestic-instapay`) reprice from Firestore (offers + `settings/shipping`); payable currency is always **EGP** (Paymob `amount_cents = totalEgp * 100`). Domestic and international shipping both use `shippingQuote` against the matching box table. The storefront checkout has no box picker. The server assigns the box and the order shipping line stays `domestic-box` or `international-box` with that `boxId`. The checkout preview prices each line from the bag's size and colour selection. **Checkout layout**: on desktop the form is the left half (signed-in email line, Delivery, Payment as separate bordered radio rows, each with the method's mark in a small box before the name, the chosen row with a 2px black border and a timeline of numbered steps under it (`.pay-steps` / `.pay-step`, built by `instapaySteps()` and `cashOnDeliverySteps()` in `features/checkout/utils/checkout-pay-steps.ts`: black number circles joined by a grey line, each step a bold title, a short grey note and its amount on the right; InstaPay: Place your order → Send the total by InstaPay (the total) → Send the screenshot on WhatsApp, with the total also on the right of its name; Cash on Delivery: Place your order → Send the delivery fee by InstaPay (the fee; left out when shipping is free) → Pay the rest in cash at your door (the cash); a large order adds "We'll contact you about the delivery fee" as step 2 and names no fee amount; a click anywhere on a row picks it through `.pay-option__hit`, an empty span stretched over the row inside the radio's label), Card dashed and disabled at the end while it is coming soon (shown at 40% opacity, like the bag tile) with "Coming soon" in muted regular text on the right, Place Order) and the order summary is the right half, sticky while scrolling (each item with photo, quantity badge, name, options and line price, then Subtotal, Shipping and Total). On phones the summary folds into a "Show Order Summary" bar with the total above the form. Item and subtotal prices come from `#pricedBag` in `checkout.page.ts`, which `orderSummary` builds on, so the rows and the totals always agree. Each bag product is read on its own (`#readProduct`): a deleted or unpublished product (permission-denied for shoppers, `published: false` for admins) comes back as `null`, its row shows "No longer available" with a remove button, it is left out of Subtotal, Shipping and Total, and Place Order refuses until it is removed ("One item in your bag is no longer available. Remove it to place your order."); any other read failure still marks the whole summary unavailable. **Egypt delivery address (AS-58)** collects only full name, city, address, and phone on the form; country stays `EG` in the payload (hidden on the form). Governorate, postal code, line 2, and region are not shown or required (stored orders keep optional legacy `governorateId`). Abroad keeps the full address fields and postal validation. Paymob secrets (`PAYMOB_SECRET_KEY`, `PAYMOB_HMAC_SECRET`) are Secret Manager only; public params (`PAYMOB_PUBLIC_KEY`, `PAYMOB_INTEGRATION_IDS`, `STOREFRONT_URL`, `PAYMOB_NOTIFICATION_URL`, `PAYMOB_BASE_URL`) are `defineString` / `.env` at deploy — never commit secrets. `paymobWebhook` (`onRequest`) verifies HMAC-SHA512 and marks `orders/{id}` `confirmed` / `failed` (idempotent via `paymobWebhookEvents/{paymob_txn_*}`). The confirmation page reads the order live (`onSnapshot` in an `rxResource`), so it follows Paymob, staff confirm and cancel without polling. Layout: a black band on top (order number and date, heading such as **Order Placed**, one short line, and the money boxes that apply: Order total, a white **Pay now**, At your door), then two columns from `@4xl`: "What happens next" steps on the left (`confirmationSteps()` in `features/checkout/utils/confirmation-steps.ts`, one list per order stage; the current step holds the InstaPay box with a small Send on WhatsApp button on the left), and Your order (photo, quantity badge, options, gifts, deal tags, Subtotal, Shipping, Total) plus Delivery (address and phone) and a Payment card (`paymentParts()` in `features/checkout/utils/confirmation-payment.ts`: the status tag next to the heading, outlined while waiting, black when Confirmed, grey for Payment Failed or Cancelled; the method's mark from `app-payment-mark` with its name; then one row per part of the payment, e.g. Cash on Delivery's delivery fee by InstaPay and the rest in cash at the door, a paid part with a check and "Paid") on the right; under the steps a black **Continue Shopping** and an outlined "Questions? Message us" button with the green WhatsApp mark. On a phone everything stacks in that order with the buttons last, full width. The InstaPay box has no logo. Its copy, the InstaPay box (amount; when both the phone number and the InstaPay address are set, a `mat-button-toggle-group.instapay-switch` (Phone Number first, `instapayWay` signal, not remembered) picks which one shows with its single Copy button, and with only one set that value shows with no switch; styled in `src/styles/ng-material/components/_button-toggle.scss`; “Send on WhatsApp”) and the WhatsApp help link come from `orderStage()` / `paymentDue()` on the live order only, never from the navigation seed. The old international bank transfer (IBAN settings, payment-proof uploads, `orderTransferRefs`) stays removed; the new **Bank Transfer** for orders shipped abroad is described in its own lines below. Admin `confirmCodOrder` (`europe-west3`; name kept, so deploys never rename a function) confirms pending Egypt cash-on-delivery **and InstaPay** orders and decrements product `stock` / `stockBySize` via `stockFields()` in one Firestore transaction (idempotent if already confirmed; staff now confirm through the status dropdown, see **Order status** below, which asks for an InstaPay payment to be seen in the bank app first). Admin `cancelOrder` cancels only **pending** cash-on-delivery or InstaPay orders (`cancelledAt`, `cancelledBy`, no email). Both are thin wrappers over `changeOrderStatus()`, the dropdown's code. Pending Paymob orders are refused because `paymobWebhook` treats `cancelled` (and `confirmed`, `shipped`, `delivered`) as final, and confirmed orders are refused. Nothing cancels unpaid orders automatically. Admin rows also have a WhatsApp button (`staffWhatsappText` for the current stage, shopper number from `shopperWhatsappNumber`; **Copy number** when it can't be converted safely). `paymobWebhook` decrements stock in the same transaction when it confirms a clean capture (`applyStockDemand` with `allowShortfall: true` in `functions/src/orders/decrement-order-stock.ts`): the payment is already taken, so a size or product that would go below 0 is floored at 0 instead of blocking the confirmation, and the order gets `needsReview: true` plus `stockIssues` (`short` or `unavailable` per product) and `stockDecrementedAt`. Stock is checked when the order is created but not reserved, so two buyers can still pay for the last item. The webhook only confirms when the signed amount equals the stored `paymob.amountCents` and the currency is exactly `EGP`; a missing amount or currency is ignored, not confirmed. Rules deny client writes to `orders/`, `orderRateLimits/`, and `paymobWebhookEvents/`. **Cash on delivery = shipping deposit first**: the shopper pays `pricing.shipping.priceEgp` by InstaPay and sends the screenshot on WhatsApp; the order goes out only after that, and the shopper pays the rest (`totalEgp − shipping`) in cash on delivery. Free shipping (fee 0) means no deposit. Admin "Confirm order" means the fee was received. Checkout, the confirmation page, and the order emails all say this with the same amounts. Order lines also save `name`, `optionLabels` (`{label, value}` per chosen option) and `imagePath` (main photo) when the order is placed (`selectionLabels()` / `mainImagePath()` in `order-pricing.server.ts`); older orders lack them, so readers fall back to the live product. Shoppers and admins see orders as `shortOrderRef()` (`#` + first 6 id characters in capitals; Angular `@core/services/orders/order-ref.ts`, functions `functions/src/email/order-email-model.ts`, keep identical).

## Bank Transfer

- **Bank Transfer (abroad, <KEY>-202)**: the payment method `bank-transfer` (name **Bank Transfer**, bank mark drawn inline in `app-payment-mark`, because the icon font subset has no bank icon) is offered only for orders shipped outside Egypt, while `isBankTransferLive()` (`STORE_INFO.payments.bankTransfer.iban` is set; `accountName`, `bankName`, `iban`, `swift` live in `functions/src/store/store-info.ts`). Bag abroad: Bank Transfer first, then Card; checkout abroad: Bank Transfer preselected with `bankTransferSteps()` (`checkout-pay-steps.ts`), Card picked only when live, and Place Order instead of the "Ordering from outside Egypt is coming soon" WhatsApp button (that shows only when neither Card nor Bank Transfer can be used).
- `createBankTransferOrder` (`europe-west3`) is the third `createManualOrder` callable (same pricing, terms, guest, App Check and rate limits as `createInstapayOrder`); it refuses an Egypt address and an empty IBAN with `failed-precondition`, and saves `paymentMethod: 'bank-transfer'`, `pricing.fulfilment: 'international-bank-transfer'` and `pricing.payIn: { currency, amount }`.
- `pricing.payIn` is the amount to send in the shopper's currency, worked out on the server: checkout sends `payInCurrency` (the currency it showed); `payInEntry()` (`functions/src/orders/pay-in.ts`) uses its `settings/currency` factor, keeps EGP unconverted when checkout showed pounds (the total checkout showed), or uses USD when the code is missing, unknown, unreliable or has no factor; `payInFor()` adds each line (`toDisplayAmount` per piece, a Buy X Get Y line as a whole, gifts 0) plus the shipping fee exactly like checkout's summary (tests: `pay-in.test.ts`). `totalEgp` stays what we expect to receive; `orderViews` carry `payIn` inside `pricing`.
- Staff confirm a Bank Transfer like InstaPay (`isManualPayment()`: same Change Status moves, Confirmed takes stock once, nothing cancels unpaid orders automatically); the confirm dialog asks for "the transfer of $205" (prices abroad include the markup, so the pounds that arrive are more than `totalEgp` and are not compared).
- `orderStage()` gives `bank-transfer-due` while it waits; `paymentDue()` then returns `reason: 'bank-transfer'` with `payIn` (InstaPay UI must check `reason`). The order page shows "Pay now" in the shopper's currency, "Send $205 from your bank" with the bank details box (Account name, IBAN in groups of 4 copied without spaces, SWIFT / BIC, Bank, Reference = short ref without `#`, Copy on each but Bank), the fee line `Choose "I pay all fees" in your bank app so the full amount reaches us.` and **Send Receipt on WhatsApp**; then "We confirm and ship".
- Emails: `bank-transfer-placed` (amount in the shopper's currency, bank details, `Choose "I pay all fees" in your bank app so the full amount reaches us.`, Send Receipt on WhatsApp, View Your Order) + `store-new-order` (Customer Sends / Order Total in EGP), and `bank-transfer-confirmed` (the shared paid email, `PAID BY BANK TRANSFER`); WhatsApp texts name the amount in the shopper's currency and the ref and never mention InstaPay or deposits.

## Guest checkout (website)

- A guest order is saved with `customerId: null`, `customerEmail` = the guest email, `guest` (terms) and `viewKey` (32 random bytes, base64url, `newOrderViewKey()`); everything else matches a signed-in order. The callables return `viewKey` (null when signed in), and the Paymob `redirectionUrl` is `orderConfirmationUrl()` (`/checkout/confirmation/{orderId}?key={viewKey}` for a guest, no `key` when signed in).
- Guest rate limits live in `orderRateLimits` next to the signed-in `{uid}_{day}` counter (20 a day, unchanged; signed-in orders never count toward the guest caps): `guest_all_{day}` (500 guest orders for the whole store), `guest_ip_{hashed ip}_{day}` (50 per connection, high because shoppers can share one mobile-network address; the IP is Express `req.ip`, the same source as `subscribeToEmails`, never the last X-Forwarded-For hop, which can be a shared Google proxy; hashed by `hashGuestOrderIp()`, never stored) and `guest_email_{sha256}_{day}` (5 per email), each with `expireAt` 2 days later for a TTL policy. Over any of them → `resource-exhausted` "Too many orders were placed today. Please try again tomorrow or message us on WhatsApp." Reaching the store-wide cap logs an error. Helpers: `order-rate-limit.ts` (pure, tested in `guest-checkout.test.ts`) and `order-rate-limit-docs.ts` (`readOrderRateLimits` / `releaseOrderRateLimits`).
- **Guest checkout (website, <KEY>-170)**: signed out, the bag's Checkout opens `/checkout`; Delivery starts with a required **Email** field (`autocomplete="email"`, checked by `guestEmail()` in `features/checkout/utils/guest-email.ts` with the server's rule) and a "Have an account? Sign In" link to `/login?returnUrl=/checkout`; signed in, the page is unchanged (account email line, saved address prefill).
- Under Place Order, for everyone: "By placing your order, you agree to our Terms and Privacy Policy." (links to `/terms` and `/privacy`, no tick box).
- A guest's checkout preview prices with `signedIn: false` (`PricingContext` in `checkout.page.ts` follows `AuthService.isAuthenticated()`), so it matches the server and never shows a signed-in-only or once-per-customer offer.
- A guest's Place Order sends `guest: { email }` (`CheckoutOrderService.placeManualOrder` / `placePaymobOrder`, `guest` is null when signed in), saves `{ key, email }` for that order in `localStorage` (`atteya-guest-order:<orderId>`, `features/checkout/utils/guest-order-storage.ts`) and opens `/checkout/confirmation/{orderId}?key={viewKey}` (Paymob returns there through its `redirectionUrl`).
- The order page takes `?key=` as an input, saves it for that order, removes it from the address bar (`replaceUrl`) only when the save worked (storage blocked: the key stays in the link, and the card's Sign In return link carries it too) and listens to `orderViews/{key}` with `onSnapshot` (`OrderViewSchema` + `orderFromView()` in `order.schema.ts`); a view that hasn't appeared yet keeps the loading state for up to 20 seconds, then "could not find". Without a key in the link it uses the saved key, else the owner read of `orders/{id}` as before.
- `app-guest-account-card` (`features/checkout/components/guest-account-card/`, under the steps of a guest order) offers **Save Your Order to an Account** after the order only: the saved email (read-only), a password, "Send me offers and new arrivals by email" (unchecked), **Create Account** (`AuthService.register` with terms accepted now; then a **Confirm Your Email** state: the confirmation link returns to the order page, and **Save to My Account** reloads the account and refreshes the ID token before `claimOrder`, since `claimOrder` reads `email_verified` from the token), **Continue with Google** (then `claimOrder`; "Saved to your account." or the server's `permission-denied` message when the Google email is a different one) and **Skip** (remembered for that order). An email that already has an account shows "You already have an account with this email." with **Sign In** back to the order page. A signed-in account with the order's email that isn't confirmed yet gets the same Confirm Your Email state (**Send Confirmation Email**, then Save).
- A link opened on another device (no saved email) shows Sign In, Continue with Google and Skip instead of the password form.
- A signed-in person on a guest order link sees **Save to My Account** (`CheckoutOrderService.claimOrder`) only when their email is confirmed and equals the saved order email (when this device knows it), and nothing when they can already read `orders/{id}` as its owner; a refused save shows the server's message.
- A Google redirect started from the card sets `sessionStorage` `atteya-claim-after-google` to the order id, and the card saves the order when the page loads again signed in.

## Store info and order stage

- **Store info (business details)**: `functions/src/store/store-info.ts` is the one place for the brand name, website, contact (`whatsapp`, `phone`, `email`), address, and social links (`instagram`, `facebook`, `tiktok`, `x`, `youtube`). Empty string = not set yet; everything that reads it skips empty fields. Edit only that file, then `npm run sync:engine`, which copies it to `src/app/core/config/store-info.ts` (`preflight` fails when they differ). It ships to the browser, so never put private details there (the store-alert inbox and API keys stay in `functions/.env` / Secret Manager). `whatsappChatUrl(number, text?)` builds the `wa.me` link, with an optional message already written. `payments.instapay` (`address`, `number`; empty until the client sends them) is where shoppers send InstaPay transfers; when both are empty every page and message says we'll send the details on WhatsApp. `payments.cardOrWallet` (`'coming-soon'` | `'live'`, read through `isCardOrWalletLive()`) is the one switch for Card (Paymob): while it is `'coming-soon'` (the default until the client's Paymob account is live) checkout lists Card greyed out with a "Coming soon" tag, a visitor shipping outside Egypt sees "Ordering from outside Egypt is coming soon" and a Message Us on WhatsApp button instead of Place Order, and `createPaymobOrder` refuses with `failed-precondition`. Set it to `'live'` (then `npm run sync:engine` and `fb:fn:*`) to bring Card back everywhere; the cart and checkout redesigns read the same switch. **Order stage (`functions/src/store/order-messages.ts`, synced to `src/app/core/config/order-messages.ts`)** is the single source of truth for what an order may show or say: `orderStage()` (`fee-to-be-agreed`, `instapay-total-due`, `instapay-fee-due`, `cod-free-pending`, `cod-confirmed`, `paid`, `paid-needs-review`, `paymob-pending`, `failed`, `cancelled`, `unknown`), `paymentDue()` (only the two due stages; the only source of InstaPay/screenshot UI), `shopperWhatsappText()` / `staffWhatsappText()` (Arabic, English digits, e.g. `1,500 EGP`, `#A1B2C3`; abroad orders never mention InstaPay, deposits or EGP amounts), and `shopperWhatsappNumber()` (Egypt mobiles → `201…`; abroad needs `+`/`00` or a local leading `0`; otherwise null). Unit tested in `order-messages.spec.ts`. The website builds its input with `orderMessageInput()` (`@core/services/orders/order-message-input`).

## Order status

- **Order status (staff, <KEY>-184)**: statuses are `pending` (Waiting for Payment), `confirmed`, `shipped`, `delivered`, `cancelled` and `failed` (Payment Failed); names in `orderStatusLabel()` (`functions/src/store/order-status.ts`, synced to `src/app/core/config/order-status.ts` by `npm run sync:engine`) and `orderStatusName()` on the website.
- The move table lives in `allowedStatusMoves()` in that file and is shared by the admin dropdown and the server: Waiting for Payment (Cash on Delivery / InstaPay only) → Confirmed, Cancelled; Confirmed → Shipped, Cancelled, back to Waiting for Payment (Cash on Delivery / InstaPay only); Shipped → Delivered, back to Confirmed; Delivered → back to Shipped; Cancelled and Payment Failed are final. Card orders are never cancelled or set back to Waiting for Payment there (refunds aren't built).
- `setOrderStatus` (`europe-west3`, admin) runs `changeOrderStatus()` (`functions/src/orders/order-status-change.ts`) in one transaction on the live order: Confirmed takes stock once (`stockDecrementedAt`; a second Confirm after a step back takes nothing), Cancelled and back to Waiting for Payment put it back per size with `applyStockReturn()` (clears `stockDecrementedAt`, stamps `stockReturnedAt`; pieces whose size or product is gone are counted in `stockNotReturned` and the snackbar asks staff to check that product), Cancelled gives offer uses back once (`offerUsesReturnedAt`) and saves the optional staff-only `cancelReason` (300 characters).
- Every move stamps `confirmedAt` / `shippedAt` / `deliveredAt` / `cancelledAt` (a step back clears the stamp of the step it left) and appends `statusHistory` (`{ status, from, at, by, byEmail?, reason? }`, in `orderStaffNotes`); orders confirmed before `stockDecrementedAt` existed count as stock taken (`orderStockTaken()`).
- `statusHistory` (with staff `byEmail`) and `cancelReason` live in `orderStaffNotes/{orderId}` (`order-staff-notes.ts`, written in the same transaction by `changeOrderStatus()` and `paymobWebhook`), not on `orders/{id}`, because the signed-in owner can read the whole order doc; rules: admin read, no client write. The admin list reads them with `OrdersAdminService.loadStaffNotes()`.
- Admin Orders: one **Change Status** menu per order (only the allowed moves, "Back to …" for a step back, which asks first), a snackbar "Order marked as Shipped.", a cancel dialog (`dialogs/cancel-order-dialog/`, optional reason, **Cancel Order** / **Keep Order**), the history and cancel reason under the order, and status tabs for every status.
- `orderStage()` has `shipped` and `delivered` stages; the order page's "What happens next" ticks Shipped and Delivered with their dates, Cash on Delivery keeps "Pay … in cash at your door" until Delivered, and a step back un-ticks the step.

## Admin Orders pages

- **Admin order details (<KEY>-213)**: the Orders list shows one short row per order (number, customer and city, item photos, payment, total, status) that opens in place, and `/admin/orders/:id` is the full order page; both show the black "Next step" bar from the order stage, Customer (email, phone, guest or account), Delivery Address (full address, shipping box), Payment (amount due, received, cash at the door, Card transaction number and paid time, amount sent from abroad), the items with photo, options, offer, unit and line price and live stock, and Subtotal, Shipping, Total (plus the EGP total for orders from abroad), built by `orderDetails()` (`features/admin/pages/orders-manager/utils/order-details.utils.ts`) from the saved order only.
- **Orders list open order (<KEY>-215)**: every list row shows a small arrow; one order is open at a time (opening scrolls it to the top); the open order is outlined black and its black bar (order number, status, customer, total, ‹ n of m › for the previous and next order, Close) sticks to the top while you scroll that order and leaves with it; Close Order also sits under the details.
- **Orders search and dates (<KEY>-256)**: `/admin/orders` has a "Search orders" field and a Date field above the status tabs (`app-orders-filter-bar`, `orders-manager/components/orders-filter-bar/`); both combine with the status tabs, and chips show each filter with **Clear All** and "3 orders" ("Newest 50 orders" when the list stopped at 50).
- Search finds a name typed in Arabic or English (no matching across scripts: "Ahmed" doesn't find "أحمد"), a phone (local, +20, Arabic digits, its start or its last 4 digits), an email or the order number (`#A1B2C3`, its start too), across every order, not only the latest 50.
- Every order saves `searchTokens` (`orderSearchTokens()` in `functions/src/store/order-search.ts`, copied to `src/app/core/config/` by `npm run sync:engine`; tests `order-search.spec.ts`), written by the order callables when the order is placed; Arabic matching ignores أ إ آ / ا, ؤ / و, ئ / ي, ة / ه, ى / ي, harakat and tatweel.
- Orders placed before <KEY>-256 get `searchTokens` from `functions/scripts/fill-order-search.mjs` (dry run by default, `--apply` to write, prod also needs `--confirm-prod`; writes only `searchTokens`, never `updatedAt`); an order without it is never found by search.
- The page asks Firestore for the longest typed word (`array-contains`) and checks the other words in the browser with the same function; with a search or dates the list is newest placed first (`createdAt`), otherwise last changed first as before; indexes `orders` (`searchTokens` contains, `createdAt`) and (`searchTokens` contains, `status`, `createdAt`).
- The Date field is a Material menu (Any Date, Today, Yesterday, Last 7 Days, This Month, Pick a Day…, Pick a Range…); Pick a Day opens `mat-datepicker`, Pick a Range opens `mat-date-range-picker` with Cancel / Apply (one day picked then Apply = that day), both under the field and stopping at today; days are whole days in the admin's own time, by the day the order was placed.

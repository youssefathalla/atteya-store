# Offers

The rules for offers, moved here from one long AGENTS.md paragraph so offers PRs stop conflicting with each other (<KEY>-157). The general Firestore, checkout and shipping rules stay in AGENTS.md.

**How to edit this file:** one fact per line, as a list item under the heading it belongs to. Add a new rule as its own line, or a new `##` heading for a new topic. Never join rules into one long paragraph: Git merges line by line, so two PRs that touch the same long line conflict even when they change different sentences.

## Who can read offers

- **Offers**: `offers/{id}` is public-read only when `active == true && visibility == 'public'`; `offerCodes` is admin-only; `offerUsage` is Admin SDK only. Offer prices are never baked into product docs: they come from the shared engine in `functions/src/offers/engine/` (edit only that copy; `npm run sync:engine` copies it to the app). Every other offer rule (top banner, overlap warnings, free gifts and the Gift Box, Buy X Get Y, one discount per item, offer limits, the price, total and ended-offer guards at Place Order, offer notes, bag bundles and the socks scripts) is in the **`offers`** skill (`.agents/skills/offers/SKILL.md`), one fact per line. Read it before changing offers, pricing, the bag, checkout or the order callables, and add new offer rules there, not here.
- `offers/{id}` is public-read only when `active == true && visibility == 'public'`; `offerCodes` is admin-only; `offerUsage` is Admin SDK only.

## Top banner (<KEY>-145)

- **Top banner (<KEY>-145)**: an offer may carry `banner` (`show`, `text` ≤ 60 characters or null = the customer title, `countdown` `hide` | `always` | `lastDays`, `countdownDays` 1–30, default 7); engine type `OfferBanner` and `parseOfferBanner()` (`engine/banner.ts`, read by both `OfferDocSchema` and `parseOfferDoc`; missing or bad = not in the banner).
- The offer editor's **Show in the top banner** switch (`banner-editor`, step 3 Extras) is disabled with "Only offers for everyone, with no per-customer limit, can show in the top banner." for signed-in-only offers and offers with a per-customer limit; switching an offer to signed-in turns it off, `saveOffer()` writes `show: false` for those and for code offers, and `validateOffer()` refuses the mix (`banner.audience`).
- An offer with a per-customer limit (`limits.perCustomer` set) is for signed-in shoppers only, so `validateOffer()` refuses it in the top banner (`banner.perCustomer`, "Offers with a per-customer limit are only for signed-in shoppers, so they cannot show in the top banner.") and `canShopOffer()` is false for it (no `/shop?offer=` page, the bag nudge opens Shop instead); search records and Sale leave it out, like signed-in-only offers (run Rebuild search after the functions deploy that brought this in).
- Tests: `functions/src/offers/engine/banner.test.ts`, `npm run test:cart`.

## Prices come from the shared engine

- **Never bake offer prices into product docs**: prices come from the shared pure engine in `functions/src/offers/engine/`, copied to `src/app/core/services/offers/engine/` by `npm run sync:engine` (`preflight` fails when the copies differ; edit only the `functions` copy).
- Algolia offer fields are display-only; checkout re-prices from Firestore on place-order.
- `onOfferWritten` and the 15-minute `refreshOfferPricing` schedule refresh them.
- `onOfferWritten` (`onDocumentWrittenWithAuthContext`) also writes one `auditLogs` entry per offer create, update and delete; `actorUid` is the doc's `updatedBy`, and for a delete (no doc left) the write's `event.authId` (`unknown` only when the write had no signed-in caller).
- Cart-level rewards and quantity tiers still show as labels only, so the offer editor hides "Buy more, save more" and "Spend X, get…" from the step 1 deal cards for launch (`REWARD_PICKER_OPTIONS`; the engine keeps them for later): an old offer of those types still opens with "This deal type isn't available yet. Pause or archive this offer." and it can't be saved (`isUnavailableDeal()` in `offers-manager/models/offer-admin.model.ts`).
- The offers list refuses **Duplicate** (and **Run Again**), and **Resume** or the switch turning on a paused offer, for those hidden deal types with the same message (`duplicateOffer`, `pauseResume` and `setOn` in `offers-manager.page.ts`); Pause, Archive and Restore still work.
- **Admin Offers list (<KEY>-219)**: `/admin/offers` shows one card per offer (`app-offer-card`, `offers-manager/components/offer-card/`) instead of a table, 3 per row from the `@5xl` container width, 2 from `@2xl`, 1 on phone; cards in a row share the tallest card's height and the footer is pinned to the bottom.
- Count boxes **Running now**, **Starting later**, **Ended**, **Archived** filter the list (`offerListBucket()`: dates decide, so a paused offer counts under Running now with "Paused"); the search box (internal name, customer title or code) and the deal-type chips (`matchesDealFilter()`: Discounts = Percent off, Amount off, Set price; Free gifts; Bundles = Bundle price, Buy X Get Y; In top banner) filter in the browser, and the counts follow them.
- A card shows the status line (`offerStatusLine()`), the deal in large text (`offerDealHeadline()`, 2 lines tall, cut off with "…"), the internal name and "Shoppers see “<title>”", then Affected products (a count only, from `matchProduct`, "108 (all)" when the offer has no conditions), Who and When (`offerWhenLine()`), then Edit (Run Again on ended cards, which duplicates) and the ⋯ menu with every old row action.
- The `mat-slide-toggle` on Running now and Starting later cards sets `active` like Pause / Resume ("Offer turned off." / "Offer turned on."); ended and archived cards have no switch.
- Offers in the same count box with the same customer title (case and spaces ignored) and the same deal type are one card (`groupOfferCards()`; the title, not the internal name, because each "Free shirt and socks" offer names its own bag internally): the card is named by that title, "Live · 6 offers", the distinct affected products of all of them, one switch for all (on while any of them is on; off turns them all off, on turns them all on), "Different dates" when their dates differ, and **Open Group** (`dialogs/offer-group-dialog/`) shows each offer as its own card with its own switch, Edit and ⋯ menu.

## Offer editor: 4 steps (<KEY>-220)

- `/admin/offers/new` and `/admin/offers/:offerId` (`offer-editor.page.ts`) are a 4-step editor: **The deal**, **Which products**, **Who and when**, **Check and start** (`app-editor-steps`, `OFFER_EDITOR_STEPS`); the saved offer document is the same as the old one-page form's for the same choices.
- Top bar: back to Offers, "New Offer" / "Edit Offer", **Save as Draft** (saves with `active: false`); each step ends with **Back** (Cancel on step 1) and **Next: <step>**, disabled while the step has an error; each error shows under the part it is about (`issueStep()` maps `validateOffer()` codes to steps).
- A finished step in the step bar is a tick and a link back; an existing offer opens on step 4 with every step finished.
- Right panel (`app-offer-summary-panel`, under the card below the `@5xl` container width): "Your offer so far" in one sentence (`offerSentence()`, grey "[which products]", "[who]", "[when]" until those steps are reached), "How the top banner will look" while the banner is on, and an example matching product priced by `displayPrice()` with its badge.
- Step 1: the deal types as `mat-radio-button` cards (`DEAL_CARDS`, only types in `REWARD_PICKER_OPTIONS`; `defaultDealFor()` gives each type's starting reward, scope and minimum), then the `reward-editor` fields (Percent off adds 10% / 20% / 30% / 50%) and "What shoppers read", filled in by `autoOfferTitle()` until staff type in it.
- Step 2: **Every product** / **Only some products**; **Include** and **Leave out** tags (`app-product-targets`, `mat-chip-grid` plus a `mat-autocomplete` picker over categories, brands and products) save as one `field in [values]` group per field (`readTargets()` / `writeTargets()`); a saved group that doesn't fit a tag (several rules, `notIn`, size, colour, price, …) shows as an "Advanced rule" tag in plain words (`describeConditionGroup()`) and **Advanced Rules** opens the `condition-group-editor`.
- Step 2 also shows the Affected products count only ("n in stock · n sold out", "n already on sale", `affectedStats()`), **See the Products** opens the list (`app-offer-preview`, at most 100 rows), and the overlap warnings in a grey box.
- Step 3: **Everyone** / **Signed-in shoppers only**, Starts (Right away / On a date) and Ends (When I turn it off / On a date, quick 3 days, 1 week, 2 weeks, End of month via `quickEndDate()`), dates picked in Cairo time with `mat-datepicker` plus a time field, "Runs for **10 days**, …" (`offerRunLine()`), then Extras: Show in the top banner (`banner-editor`), Limit how many times it's used (**Set a Limit**), and More settings (`offer-settings`: Products already on sale, Badge override, Priority).
- Step 4: the deal and `offerCheckSentence()` in a black box, rows with **Change** links, **Good to know** (every warning plus products already on sale), **Name for your team** filled in by `autoTeamName()` ("T-shirts 15% · late November") until staff type in it, and **Save, Don't Start** (`active: false`) beside **Start Offer** / **Schedule Offer** (start in the future) / **Save Changes** (editing an offer that was on).

## Offer product picker: a product once, then its colours (<KEY>-270)

- Every offer product picker uses `app-product-targets`: step 2 Include / Leave out, Bundle & Save groups, Bundle price and Buy X Get Y (step 2 tags), Buy X Get Y "One of these products" (`kinds="products"`, `[expandModels]="true"`, saved in `getConditions`) and each Free gift's choices (`kinds="products"`, `[expandModels]="true"`).
- The search lists each product once (all colours of one `modelGroup` together, `groupOfferProducts()` in `offers-manager/models/offer-product-picks.ts`, pure, tested by `npm run test:cart`), with "3 colours" next to a product with several; an empty box lists Categories, Brands and Products (up to 60 each, the list scrolls), typing narrows to 8 each.
- Enter adds the top match (`autoActiveFirstOption`); Enter with no match does nothing.
- A product with 2 or more colours gets its tag ("Nox Padel Shorts · All colours" / "Nox Padel Shorts · Black, White", `productPickLabel()`) and a small card (`.offer-colour-pick`: the name, "All 4 colours" or "2 of 4 colours", a remove button) with a **Colours** `mat-select multiple` under it, as wide as the search box (full width on phone); the closed field shows only round colour dots, no names (`.offer-colour-dot`, the name as a tooltip and for screen readers), or one multicolour dot for All colours; the open list keeps the names: "All colours" first and ticked by default, then that product's colours with their dots (`nextColourChoice()`: ticking a colour unticks All colours, ticking All colours clears the colours, unticking every colour goes back to All colours).
- All colours is saved as a `modelGroup` rule (target field `modelGroup`, `writeProductPicks()`), so a colour added to that model later is in the offer; specific colours, and a product with one colour, are saved as `productId`s.
- An offer saved before this (several `productId`s of one model) opens grouped as that product with those colours ticked (`readProductPicks()`); unknown ids and models are kept as they were.
- Free gifts and the Buy X Get Y free item name products (the bag's free-pick tiles need product ids, `freeItemProductIds()`), so there All colours saves every colour shown on the store today (`expandModels`; hidden colours are left out unless every colour is hidden), and a choice holding every shown colour reads as All colours; a colour added later joins only when the offer is saved again.
- Colour names come from each colour's first `colors` entry; when two colours of one product share it (look-alikes with an accent colour) both show every colour ("Black & White"); hidden colours show "(hidden)" in the Colours dropdown.
- `coversOneProduct()` (`offer-shop.ts`) counts one `modelGroup` value like one product id, so a Buy X Get Y on one product with All colours keeps the bag's "Add 1 more to get 1 free" and **Add 1**.
- `CatalogNames.models` (model → product name, `modelNames()`) names `modelGroup` tags in the sentences; the Advanced Rules editor calls the field "Product (all colours)" and lists "Specific product" choices as "Nox Padel Shorts · Black".

## Overlap warnings

- **Overlap warnings:** the offer editor's overlap box (step 2) and Good to know (step 4) have one line per other offer that is on or scheduled (not paused, archived or ended; any audience or coupon code) and shares products with the one being edited, saying what shoppers get (`overlapMessage()` in the engine's `validate.ts`, tests `validate.test.ts`): two price offers (Percent off, Amount off, Set price) "Shoppers get whichever is cheaper."; a price offer and Buy X get Y "Shoppers get whichever saves them more, never both."; a Free gift with a price offer "n products also have "<other>". Shoppers get both: the discount and the free gift.", with Buy X get Y "Each item gets either the free gift or the Buy X get Y discount, whichever is worth more."; two Free gift offers "Only the higher-priority gift offer applies."; two Buy X get Y offers "Each item counts toward one Buy X get Y offer only, the higher-priority one first.".
- Free shipping, tiered, cart offers and offers with a minimum never warn.
- A scheduled offer's line ends with " (starts <Cairo date>)" (`formatCairoDate()`).
- Warnings never block saving.

## Bundle price (<KEY>-198)

- **Bundle price** (`reward.kind: 'bundlePrice'`, `rows: [{ quantity, price }]`): a whole-EGP total per number of pieces ("2 for EGP 200", "3 for EGP 275") for any products staff pick; an item offer with no minimum (the form saves `scope: 'item'`, `minimum: null`) with the same settings as every other offer (audience, schedule, limits, coupon code, top banner, priority, Products already on sale).
- Offer editor (step 1 card **Bundle price**, `reward-editor`): a **Price per quantity** list of rows ("Pieces" + "Total price (EGP)"), **Add Row** and a bin per row; rows are sorted by pieces when the Pieces field is left. `validateOffer()` needs 1 to 10 rows (`MAX_BUNDLE_ROWS`), pieces 1–20 (`MAX_BUNDLE_PIECES`), each row's pieces different, totals whole EGP above 0 (`reward.bundleRows`, `reward.bundlePieces`, `reward.bundleDuplicate`, `reward.bundlePrice`). A 1-piece row is optional.
- Readers drop bad rows (`bundleRows()` in the engine's `bundle-price.ts`, used by `parseOfferDoc` and `OfferRewardSchema`); an offer left with no rows prices nothing.
- `priceBagDeals()` prices bundles with Buy X Get Y, so the bag, checkout and the order callables charge the same: per offer (highest priority first, each piece used by one offer only) the qualifying pieces not used yet, any mix of the offer's products and sizes, most expensive first after per-item offers, go into the cheapest mix of rows for the shopper (`bestBundle()` / `bundleCover()`; rows repeat: rows 1 = 125, 2 = 200, 3 = 275 and 4 pieces = 3-row + 1-row = 400, 6 pieces = two 3-rows = 550); a piece no row can cover pays its own price.
- One discount per item: a piece in a bundle pays its share of the bundle total and gets no Percent off, Amount off or Set price; the bundle is used only when it costs less than those pieces with their per-item offers (a tie keeps the per-item offers). With a Buy X Get Y offer on the same pieces the bag is priced bundles-first and deals-first too and the cheapest bag wins (a tie keeps priority order), never both on one piece.
- Pieces in a bundle keep their free gifts (a gift is not a discount for this rule).
- Shares are split by the pieces' own prices in whole EGP that add up exactly, the extra pounds on the first pieces (`splitBundleTotal()`: 275 for three pieces of 175 = 92 + 92 + 91). Each line's `BagLineDeals.deals` gets `{ offerId, units, percent: 0, discount, bundle: true }`; `dealUnits` counts the pieces (they pay `basePrice` before the share); `dealTag()` shows "Bundle price" for such an entry (confirmation page, admin Orders, emails).
- `BagDeals.bundles` lists each bundle (`BagBundle`: `rows` used with `count`, `units`, `total`, `saving` against the pieces' own prices, `lineIndex` = the last bag line that counts toward it, `next` = the next bigger row and the pieces `missing`, only when adding more of the last line's item really puts more pieces in the bundle; null at the top row).
- Bag (`app-cart-drawer`): each piece shows its share as the line price with its normal price struck through; under the last item of the bundle, one grey strip "<title> · 2 for EGP 200" ("2 × 3 for EGP 275 + 1 for EGP 125" for several rows) with "You save EGP 150", then while a bigger row exists a dashed nudge "Add 1 more to get 3 for EGP 275" with **Add 1** (filled; more of that last item) and **Choose Another** (outlined; `/shop?offer=<id>`, plain `/shop` when `canShopOffer()` is false); the buttons wrap under the text on a narrow phone (`.bag-card__strip--wrap`, `.bag-card__strip-actions`). Wording: `bundleStripTitle()` / `bundleNudgeText()` / `bundleRowLabel()` in `@core/services/offers/offer-shop` (tested by `npm run test:cart`); amounts in the visitor's currency through `formatMoney` (house style "EGP 200").
- One piece with no 1-piece row: full price, no strip, and the nudge to the smallest row.
- Shop's `?offer=` heading for a bundle shows the offer title and `offerShopSubtitle()` lists its rows ("2 for EGP 200 · 3 for EGP 275", in the visitor's currency).
- Product page: one line under the price with the offer title (like Buy X Get Y), a link to `/shop?offer=<id>` when `canShopOffer()`; cards: `displayPrice()` uses the 1-piece row for "From" (`partial: true`) and lists the offer in `offerIds`; it never puts a product in Sale (`SALE_OFFER_KINDS`).
- Product page picker (<KEY>-199, `app-product-bundle-picker`, `features/product/components/product-bundle-picker/`, pure helpers in `features/product/utils/product-bundle.ts`): on a product in a live Bundle price offer (`bundleOfferForProduct()`: live for this shopper, `scope: 'item'`, no minimum, matching the product; highest priority, then newest edit, like the bag) it replaces the single Add to Bag with one bordered radio row per bundle row (`.pdp-bundle-row`, chosen row `--selected` 2px black border): "Get 2 for EGP 200", the price per piece with this product's price struck through and a `.deal-tag` "Save n%" (`bundleSavePercent()`, against the product page price after item offers).
- When the offer has no 1-piece row, the picker adds "Get 1 for <the piece's own price>" first (no Save tag), so one piece can still be bought; the 1-piece row is always picked first.
- The picked row opens one step per piece ("Piece 1", "Piece 2", …), each a sideways row of Gift Box cards (`.pdp-gift-card`, `appHorizontalScroll`, `app-row-scroll-nav`); piece 1 starts on the product being viewed, whose size and gifts come from the page's own options and Gift Box above; another product with sizes gets a "Piece 2 size" step (only sizes with stock, `toGiftChoice()`).
- The cards are this product, then up to 20 of the offer's published, in-stock products from Algolia (`offerIds:"<id>" AND inStock:true`, `browseCatalog({ distinct: false })` so every colour is its own card), each read from Firestore and passed through `toGiftChoice()` (a product with a real choice besides size is left out); an offer Shop can't list (`canShopOffer()` false) offers this product only. Read in the browser only; the server and loading render a skeleton the picker's size.
- Add to Bag reads "Add to Bag · EGP 125" / "Add 2 to Bag · EGP 200" (visitor's currency); with a piece open it adds nothing and shows "Choose piece 2 first." / "Choose a size for piece 2 first." under that step and focuses it; when all are chosen it adds one line per piece in one change (`CartService.addAll()`, all or nothing when the bag is full) and the bag prices the bundle as above. If the products can't be read, the page falls back to the normal Add to Bag.
- Orders: `withDeals()` saves the bundle entries on the line (`deals[].bundle: true`, `percent` 0, `discountEgp`, plus `fullEgp` and `discountEgp` on the line); `deals.offerIds` includes the bundle, so `dealOfferIds` (the Buy X Get Y guard), the ended-offer guard and the price, base and total guards cover it; offer limits count it once per order as `UsedOffer.kind` `'bundle'`, and cancel gives the use back like any other kind.
- Overlap warnings: a bundle with a price offer or a Buy X Get Y offer "Shoppers get whichever saves them more, never both."; two bundles "Each item counts toward one Bundle price offer only, the higher-priority one first."; with a Free gift "Shoppers get both: the discount and the free gift."
- Engine tests: `functions/src/offers/engine/bundle-price.test.ts` (1, 2, 3, 4, 6 and 7 pieces, with and without a 1-piece row, mixed products, per-item offers, Buy X Get Y, sale items, nudges, the card price, validation and parsing).

## Bundle & Save (<KEY>-252)

- **Bundle & Save** (`reward.kind: 'bundleSet'`): 2 to 4 groups (`slots: [{ id, name, quantity, conditions }]`, each group's products, category or brand and how many pieces, 1 to 5), and one piece set from every group gets `setReward`; `maxSets` caps the sets (null = no cap). An item offer with no minimum, like Bundle price.
- `setReward` is `{ type: 'total', price }` (the set costs that many EGP), `{ type: 'percent', percent }` (1–90), `{ type: 'amount', amount }` (EGP off the set) or `{ type: 'cheapestFree' }` (the cheapest piece of the set is free).
- The engine file is `functions/src/offers/engine/bundle-set.ts` (rules, matching, set total and shares); the bag pricing (`priceBundleSet()`) lives in `buy-x-get-y.ts` next to Bundle price and Buy X Get Y.
- `validateOffer()` and the readers share `bundleSetProblems()`: fewer than 2 or more than 4 groups, a group quantity outside 1–5, a group with no products, category or brand, a group over the rule caps (10 rule groups, 10 rules, 200 values), an empty or long group name, two groups with one id (ids and names are trimmed first), a percent outside 1–90, a price or amount that is not whole EGP above 0, or `maxSets` below 1 (codes `reward.bundleSlots`, `reward.bundleSlotPieces`, `reward.bundleSlotProducts`, `reward.bundleSlotRules`, `reward.bundleSlotName`, `reward.bundleSlotId`, `reward.bundleSetPercent`, `reward.bundleSetAmount`, `reward.bundleSetPrice`, `reward.bundleMaxSets`).
- Both readers (`parseOfferDoc` on the server, `OfferRewardSchema` in the app through `v.looseObject`) call the engine's one reader, `readBundleSet()` (group rules through `readOfferConditions()` in `engine/read-conditions.ts`, which is also the server's reader for every offer's rules), then `cleanBundleSet()`: a bad reward keeps the offer with no groups, so it prices nothing and covers no product, the same in the bag and the order callables. A missing `maxSets` reads as no cap.
- A product is in a Bundle & Save offer when it matches the offer's own rules (usually none) and at least one group (`bundleSetMatch()`), so an offer with no rules of its own still covers only its groups' products.
- `offerMatch(offer, product)` (engine `item-price.ts`) is the one check of "is this product in this offer" for every kind: cards and Shop's `?offer=` (`displayPrice`), label badges, overlap warnings, the product page and its resolver, the admin offer list, offer preview and the product editor's running offers. Use it instead of `matchProduct(offer.conditions, …)` for a whole offer.
- The product page shows a live Bundle & Save offer as an offer line with its title, a link to the offer's page `/bundle/<id>?product=<product id>` (<KEY>-279; before that `/shop?offer=<id>`, <KEY>-254; the picker is <KEY>-255).
- Product page section (<KEY>-255, `app-product-bundle-save`, `features/product/components/product-bundle-save/`, pure helpers in `features/product/utils/product-bundle-save.ts`): on a product in a live Bundle & Save offer for this shopper (`bundleSaveForProduct()` over the engine's `bundleSetOffersForItem()`: live, `scope: 'item'`, no minimum, the product fits the offer and a group (`bundleSetSlotFits()`, the bag's own `qualifies` rules); highest priority, then newest edit, like the bag, skipping offers `canShopOffer()` refuses; worked out for the product, not its chosen size, so changing size never moves the group or clears picks) a **Bundle & Save** box shows under the options (after the Gift Box and Bundle price picker), above the normal Add to Bag, which still adds this product alone.
- Its black header has the offer title and the saving (`bundleSaveHeaderSaving()`: "Save EGP 300", "Save 15%", "Cheapest item free", "All for EGP 4,500", in the visitor's currency), then one numbered step per piece in group order ("1. Racket", "2. Ball 1", "3. Ball 2"): the product being viewed fills the first piece of its group ("This racket ✓", `thisProductPhrase()`; its size and gifts are the page's own choices above), every other piece is an `app-choice-card-row` of the products that fit that group, plus an `app-choice-size-row` step once a product with sizes is picked.
- Its cards: published, in-stock products of the offer (Algolia `offerIds:"<id>" AND inStock:true`, `distinct: false`, up to 60 for all groups together, read in the browser only, each from Firestore through `toGiftChoice()`), split per group by `bundleSaveSlotChoices()` (`choicesThatFit()`, shared with the Bundle price picker) with only the sizes the bag would count in that group, up to 20 per group. The server and loading show a skeleton of the box; a failed read, or a group with no product (other than this product's own piece), hides the section.
- **Add Bundle to Bag · EGP 4,900** shows the price `priceBag()` gives those pieces on their own once every piece's product is picked (gifts left out); with a piece or this product's own choice still open it adds nothing and asks under that step ("Choose a bag first.", "Choose a size for the bag first.", "Choose ball 2 first."; prompt keys `set:<piece>` / `set-size:<piece>`), a size (or colour) of this product its group doesn't take asks "This size isn't part of the bundle. Choose another size." at the size choice (the own step shows ✓ only once this product's choices fit); otherwise it adds one line per piece through `CartService.addAll()` (all or nothing when the bag is full) and the bag prices them as a set.
- `priceBagDeals()` per Bundle & Save offer (highest priority first, each piece used by one offer only): it counts the most complete sets the free pieces make (a piece that fits several groups goes where every set can still be completed, Hall's rule in `demandFits()`, counted per bag line), capped by `maxSets`, fills them with the most expensive pieces after per-item offers (`pickForSets()`, like Bundle price), and puts each group's most expensive pieces in the first set.
- One discount per item: a set gets the saving only when it costs less than its pieces with their own Percent off, Amount off or Set price offers (a tie keeps those). When a set loses, the piece whose per-item offer saves most is left out and the sets are planned again without it, so a losing set never uses up `maxSets`; pieces left out keep their own prices, and another offer may still use them.
- With Bundle price or Buy X Get Y offers in the same bag, `priceBagDeals()` tries every order of the three kinds (each kind keeps its priority order) and keeps the cheapest bag; a tie keeps plain priority order. Bags without Bundle & Save price exactly as before.
- Pieces in a set keep their free gifts; free gifts still come on top.
- Each piece pays its share of the set total (`bundleSetShares()`: `splitBundleTotal()` by the pieces' own prices, whole EGP that add up exactly; with the cheapest piece free that piece pays 0 and the others their own price). Each line's `BagLineDeals.deals` gets `{ offerId, units, percent: 0, discount, bundle: true, set: true }`.
- `priceBag()` (`@core/services/cart/cart-deals`) passes `sets` through with `lineIndex` pointing at the bag line, like `bundles`, and empties a set's `missing` when completing it can't beat its pieces' own offers (`bundleSetNudgeLoses()`: certain only for an amount off, when the smallest per-item savings of the offer's pieces outside a deal already reach the amount).
- Bag (`app-cart-drawer`, <KEY>-254): each piece in a set shows its share as the line price with its normal price struck through, a free piece "Free"; under the set's last item one grey strip with the offer title ("Padel kit · 2 bundles" for more sets) and "You save EGP 300".

## Offer limits (<KEY>-133)

- Offer limits (`limits.totalUses`, `limits.perCustomer`) count orders, once per offer however many gifts or pieces, for every offer type an order uses (<KEY>-133; `UsedOffer.kind` in `offer-usage.ts`, collected by `addUsedOffer` in `order-pricing.server.ts`): a Free gift it gives gifts from (`gift`), a Buy X Get Y offer that discounts it (`deal`), a Percent off, Amount off or Set price offer that lowers at least one piece the order pays for (`item`; pieces in a Buy X Get Y group that won don't count, since they pay the price before it), and a Free shipping offer only when it made the shipping free (`shipping`, `freeShippingOfferIdOf()`: not when the box fee, the Settings promo or free-over was already as low, nor when the box itself costs 0); an offer with no limits is not counted at all (nothing reads its counts, and a store-wide sale would otherwise make every order write the same `offerUsage` document), so a limit added later counts orders from then on: `readOfferUses` (`functions/src/orders/offer-usage.ts`) checks and bumps `offerUsage/{offerId}` and `offerUsage/{offerId}_{uid}` in the order transaction (Paymob: in the rate-limit reservation, given back by `releaseOfferUses` if the payment can't start); a failed Paymob payment does not give its uses back.
- Cancelling a Cash on Delivery or InstaPay order (Waiting for Payment or Confirmed, through `changeOrderStatus()`, <KEY>-184) gives its offer uses back (<KEY>-172): the order saves `offerUses` (`offerIds`, the `customerKeys` it counted under, and `switchedOffIds`, the offers its last use switched off; `savedOfferUses()` in `offer-usage.ts`) when it is placed, and the cancel (`readOfferGiveBack()`) takes 1 off `offerUsage/{offerId}` and each `offerUsage/{offerId}_{key}` (never below 0) in the cancel transaction and switches back on a saved `switchedOffIds` offer only while it is still off with `updatedBy: 'system:offer-limit'` (one staff switched off stays off); it stamps `offerUsesReturnedAt`, so nothing is given back twice, and orders placed before `offerUses` existed give nothing back.
- An offer with a once-per-customer limit (`limits.perCustomer` set) is only for signed-in shoppers, whatever its audience: `liveOffers` leaves it out when `ctx.signedIn` is false, so visitors never see its price and guest orders never get it (Youssef, Nov 10, 2026; a guest's typed email proves nothing, so a per-email count could be used up by a stranger or dodged with another email). A guest's `readOfferUses` key is still `guestOfferCustomerKey(email)`, but only `totalUses` can apply to a guest order.
- Signed-in orders count `perCustomer` uses under the uid only (`OrderCustomer.offerKeys`); `readOfferUses`, `confirmedEndedOfferIds` and `releaseOfferUses` also accept several keys and check the highest count.
- Guests are priced with `signedIn = false`: an offer with `audience: 'signedIn'` never applies to a guest order; every other offer applies exactly as for a signed-in shopper.
- Signed-in-only offers (and once-per-customer offers) need a confirmed email (Youssef, Nov 10, 2026): the order callables price with `signedIn = offerPricingSignedIn(caller)` (`functions/src/orders/offer-signed-in.ts`: signed in **and** ID token `email_verified`), so an account whose email is not confirmed is priced like a guest. - The website prices every storefront `signedIn` flag with `AuthService.offerSignedIn()` (signed in and `email_verified`; product page, cards, search, favourites, the bag, checkout and `OffersService.live`), never `Boolean(user())` or `isAuthenticated()`, so it shows exactly what the server charges. The admin offer preview and editor keep their own flag.
- The order that takes an offer's **last** `totalUses` use also switches that offer off in the same transaction when it is still on (`active: false`, `updatedAt`, `updatedBy: 'system:offer-limit'`; an offer staff already paused is left alone), so the live offers listener takes it out of every bag, product page and checkout; a Paymob start that fails switches it back on (only when `updatedBy` is still that marker).

## One discount per item (<KEY>-137)

- **One discount per item (<KEY>-137):** Buy X Get Y groups are built one at a time on `basePrice`, and each group's pieces get either the Buy X Get Y discount or their per-item offers (Percent off, Amount off, Set price), whichever saves the shopper more in total (a tie keeps the per-item offers), never both (`dealWins()` in `buy-x-get-y.ts`; paid pieces are picked from those whose per-item offers save least).
- A group that loses gives no discount, is not in `offerIds` (so `dealOfferIds` and offer limits don't count it) and its pieces may still be used by another Buy X Get Y offer; pieces outside every group keep their per-item offer.
- A free item from a category or brand (no product list) gets no "add the free item" nudge while the bought pieces' per-item offers save anything, because the bag can't know the free item's price (`otherItemMustBeat` in `nextGroupHint`).
- Each line's `BagLineDeals.earns` lists, for its pieces bought in a group that won, the other lines whose pieces that group made free or cheaper (`offerId`, `units`, `percent`, `freeLines`); a line that has a per-item offer it gave up for that shows a one-line label under its name (`.bag-card__earned`, `deal-tag` size): "Gets you the free bag" / "Gets you 50% off the bag", the free item's category as a short lower-case singular word (`shortItemWord()` / `earnedItemLabel()` in `@core/services/offers/offer-shop`, at most `EARNED_LABEL_MAX` 28 characters, else "Gets you a free item" / "Gets you 50% off an item"; tested by `npm run test:cart`).
- Each line's `BagLineDeals` says `dealUnits` (pieces in a group that won: they pay `basePrice`), `offerUnits`, `before` and `total`; the bag shows the per-item offer strip only for `offerUnits` pieces and the deal tag only when a group won, and a same-items `add-more` nudge is left out when the next group would lose too.
- Free gifts and free shipping are not discounts for this rule and may come on top.
- A Free shipping offer qualifies only when at least one bag line passes `matchVariant(conditions, exclude, line.product, line.variant)` in `shippingQuote` (`engine/shipping.ts`), so Except rules always apply: an "all except Brand X" offer never frees a bag of only Brand X items (<KEY>-158; tests in `shipping.spec.ts`). Without lines, only an offer with no product rules and no Except rules qualifies.
- A bag that mixes qualifying and excluded items still ships free: one qualifying line is enough, and adding excluded items (for example a Black one to an "all except Black" offer) never takes free shipping away (Youssef, Nov 11, 2026, <KEY>-191).
- `ShippingQuoteInput.lines` are `ShippingQuoteLine`s (`{ product, variant }`): the paid lines with the size and colour chosen (checkout uses `bagLineVariant()`, the order callables the same variant they price the line with), so size and colour Except rules apply at the chosen option, as for every other offer type: "all except Black" never frees a bag of only a multi-colour product in Black (<KEY>-159; tests in `shipping.spec.ts`).

## Offer notes (<KEY>-143)

- **Offer notes (<KEY>-143):** when an offer that was giving the bag something stops applying during the visit (ended, paused, archived, its time is up, or checkout was refused because it is full), the bag (above the items) and checkout (above the summary) show one note per offer: "The <offer title> offer has ended, so your total changed." or, when the refusal says this shopper used it up (`details.reason: 'used'` from `offerFullError`, read by `endedOfferReasonFrom()` and passed to `OffersService.markEnded(id, 'used')`), "You've already used the <offer title> offer, so your total changed."; a free gift that can no longer be given shows "Your free shirt is no longer available." under its item instead of its row.
- **Sold-out gift on first look (<KEY>-164):** a picked free gift whose product is already gone or sold out when the bag or checkout first prices it (`BagOfferState.unavailableGifts`, from `bagOfferLook`) gets the same note under its item on the first look too (offer-ended notes still never show on the first look); checkout never lists it as "Free", leaves it out of the parcel weight (only gifts `bagOfferLook` says are given are weighed), and Place Order refuses with `unavailableGiftsMessage(count)` ("One free gift in your bag is no longer available. Remove the item and choose another gift." / "2 free gifts in your bag are no longer available. Remove those items and choose other gifts."). `giftNoteText` says "are" for a plural name ("Your free socks are no longer available.", `isPluralName`).
- Notes are only for a change seen during this visit (never on first load, sign-in or sign-out), close with ✕ (aria-label "Dismiss") and go away when the bag changes; an offer that just lost to a better one gets no note.
- Free gift offers never get an "offer" note (a gift doesn't change the total).
- After any `failed-precondition` refusal checkout reads its products again (`isFailedPrecondition()`), so a sold-out gift shows.
- `BagOfferNotesService` and the helpers are in the `reusable-catalog` skill.
- Pieces in a group pay the price before per-item offers, so each order line also sends `shownBaseEgp` (`shownLinePrices()`), and `missedBasePrice()` refuses with `details.priceChanged` when that price went up on a line with pieces in a group (a Set price offer would otherwise hide the rise from `missedLinePrice`).
- A request with no `shownBaseEgp` (a page from before this rule, which stacks Buy X Get Y on per-item offers) is never given the stacked price: when `costsMoreThanStacked()` says the bag now costs more, `outdatedPageError()` refuses with "Prices in your bag changed. Refresh the page and place your order again." (`details.outdatedPage`).
- `priceStoreOrder` runs the same engine on the server, so a client can't fake a discount: a line with pieces in a group keeps `unitEgp` (after per-item offers), has `lineDisplay` after the discount, and saves `fullEgp` (the line before the discount, with group pieces at the price before per-item offers; readers use it for the struck price and fall back to `unitEgp × quantity` on older orders), `discountEgp` plus `deals` (`offerId`, `units`, `percent`, `discountEgp`); gifts are resolved and saved for `giftUnits` pieces only.
- The confirmation page, admin Orders ("Offer · Free") and emails (a tag on the item card, the line price after the discount) read those fields.

## Ended offers at Place Order

- An order is never charged more than the shopper saw: when an offer the order uses (Buy X Get Y, Percent off, Amount off, Set price or Free shipping) is already full (every use gone, or this shopper's `perCustomer` uses), `readOfferUses` refuses with `failed-precondition`, the message "The <offer title> offer has ended, so this order's total changed. Check your bag and place your order again." (or "You've already used the <offer title> offer, …") and `details.endedOfferId`.
- Checkout (`endedOfferIdFrom()` in `@core/services/orders/order-refusal`, tested by `npm run test:cart`) shows that message and calls `OffersService.markEnded(id)`, which leaves the offer out of `all()` (bag, checkout summary, product page) for the rest of the visit, and every order request sends `endedOfferIds` (`OffersService.endedIds()`).
- `priceStoreOrder` leaves one of those offers (any type except Free gift, whose full offer asks the shopper to add the item again instead) out of all its pricing (per-item prices, Buy X Get Y, shipping) only when `confirmedEndedOfferIds()` (`offer-usage.ts`) reads its `offerUsage` counts and finds no use left for this shopper; any other id is ignored, because with two Buy X Get Y offers on the same items dropping one that still has uses could let a bigger, lower-priority discount win.
- The shopper then places the order again at the total they now see.

## Buy X Get Y guard at Place Order

- Every order request also sends `dealOfferIds` (the Buy X Get Y offers checkout's summary applied, `dealOfferIdsOf()` in `@core/services/cart/cart-deals`); when the server's pricing doesn't apply one of them (`missedDealOfferId()` in `order-pricing.server.ts`), `priceWithFreshOffersOnMiss()` first reads the offers again without the 60-second `getActiveOffers()` cache (staff may have just created or widened the offer) and prices again; if it still misses, `missedDealError()` refuses instead of charging more than the summary showed: an offer that is no longer live by the server's clock and rules (`liveOffers`: its time is up while the shopper's clock is behind, not started, paused, archived, gone, audience or code no longer match) is refused as ended ("The <offer title> offer has ended, …", `details.endedOfferId`), and only an offer that is live but still not applied gets "Prices in your bag changed. Check your bag and place your order again." with `details.changedOfferId`.
- Checkout (`offerToLeaveOut()` in `@core/services/orders/order-refusal`) calls `markEnded` for every `endedOfferId`, and for a `changedOfferId` only when the same one comes back twice in a row on one visit, so Place Order never fails forever.

## Price guard for Percent off, Amount off and Set price (<KEY>-139)

- **Percent off, Amount off and Set price offers get the same guard (<KEY>-139):** each order line also sends what checkout showed for one piece (`shownUnitEgp`, after per-item offers and before Buy X Get Y) and the per-item offer behind it (`shownOfferId`), from `shownLinePrices()` in `@core/services/cart/cart-deals` (parsed by `parseShownUnitEgp` / `parseShownOfferId` in `order-request.ts`; a line without them, from an older page, is not compared).
- When the server's unit price is higher (`missedLinePrice()` in `order-pricing.server.ts`), `priceWithFreshOffersOnMiss()` reads the offers again without the cache and prices again; if it is still higher, `priceChangedError()` refuses with "Prices in your bag changed. Check your bag and place your order again." and `details.endedOfferId` (the shown offer is no longer live on the server), `details.changedOfferId` (live but no longer gives that price) or `details.priceChanged` (the product price went up: no offer was shown, or the shown offer still applies, in which case `changedOfferId` comes too; checkout reloads its products, `priceChangedFrom()` in `order-refusal`).
- A lower or equal server price goes through at the server's price; the shown price never lowers anything.
- Tests: `functions/src/orders/order-price-check.test.ts`.

## Shipping fee and total guard (<KEY>-147)

- **The shipping fee and the order total get the same guard (<KEY>-147):** every order request also sends `shownShippingEgp` and `shownTotalEgp` (whole EGP, from the checkout summary's `shown`; while the fee is to be agreed, `shownShippingEgp` is null and `shownTotalEgp` is the items total), parsed by `parseShownAmountEgp` in `order-request.ts`.
- After pricing, `missedOrderTotal()` in `order-pricing.server.ts` compares them with the server's shipping fee and `totalEgp` (a value not sent is skipped), because a lower price can drop the bag under the free-shipping amount, shrink a Buy X Get Y discount or make a piece keep its free gift instead, while every line passes.
- When either is higher, `priceWithFreshOffersOnMiss()` reads the offers again without the cache; if it still misses, `totalChangedError()` refuses with "Prices in your bag changed. Check your bag and place your order again." and `details` `priceChanged: true`, `totalChanged: { shippingEgp, totalEgp }` and `nowMs` (the server's clock).
- A lower or equal server amount goes through at the server's total.
- **Fee to be agreed (<KEY>-152):** a `domestic-agreed` order compares only its items total (`totalEgp`, fee 0) with `shownTotalEgp`, so a shrunk Buy X Get Y discount or a kept free gift can't save it for more than the "+ shipping" amount checkout showed.
- When checkout showed a fee to be agreed (`shownShippingEgp` null, `shownTotalEgp` set) but the server's weights fit a box with a fee above 0, that is a miss too and is refused the same way; a free box goes through.
- Checkout's to-be-agreed branch (`feeToBeAgreedSummary()` in `checkout.page.ts`) shows the server's items total when the same refusal comes back twice in a row, or the server's box fee and total (`serverTotalsSummary()`) when the server fitted a box.
- Checkout (`@core/services/orders/order-refusal`: `totalChangedFrom`, `serverClockFrom`, `serverTotalsToShow`, tested by `npm run test:cart`) reads the products again, calls `OffersService.syncClock(nowMs)` (the offer clock ticks at once and keeps the server's offset when it is 10 seconds or more off, so a device with a wrong clock prices offers like the server) and, when the same server totals come back twice in a row, shows them in the summary (Subtotal, Shipping, Total and the payment steps) while its own figures stay the same, and sends them, so Place Order never fails forever.
- Bag and checkout price with `OffersService.now()` (the offer clock, moved every minute), so an offer whose time is up stops discounting without waiting for the bag to change.

## Previous Versions

- **Previous Versions (<KEY>-251)**: every write of `settings/navigation` or `settings/home` keeps the version it replaced: `onNavigationSettingsWrite` / `onHomeSettingsWrite` (one per doc, `functions/src/settings/settings-history.trigger.ts`, `europe-west3`, `retry: true`; pure rules in `settings-history.ts`, tested in `settings-history.test.ts`) copies the before-data to `settingsHistory/{docId}/versions/{event id}` as `data`, with `savedAt` (its `updatedAt`, else the trigger time), `replacedAt`, `savedBy` / `savedByEmail` (its `updatedBy`, email from Auth) and `summary` ("6 menus, 41 links", "3 hero slides, 3 shop cards, 6 category links").
- A save that changed nothing but `updatedAt` / `updatedBy` keeps no version (`sameSettingsContent()`); the trigger keeps the newest 30 versions per doc (`MAX_SETTINGS_VERSIONS`) and deletes older ones in the same run; rules: `settingsHistory/{docId}/versions/*` read by `canManageStore()`, no client write (admins included), and `settingsHistory` is left out of the catch-all; the list query (`replacedAt` desc) needs no composite index.
- Both saves write `updatedBy` (the saver's uid): `NavService.updateNavigation(categories, updatedBy)` and `HomeService.updateHomeSettings(settings, updatedBy)`; `firestore.rules` refuses a create or update of `settings/navigation` or `settings/home` whose `updatedBy` isn't the caller's uid.
- Admin → Navigation and Admin → Home Page have **Previous Versions** instead of Reset to Defaults: `<app-previous-versions-dialog>` lists the versions newest first; **Restore This Version** loads it into the editor as an unsaved draft (`loadVersion()` on each draft service) with "Restored the version from 12 Nov, 14:07. Review it, then Publish to Store."; nothing goes live until Publish to Store, and that publish is kept as a version too.
- Restore This Version on a page with unpublished edits first asks "Replace Your Unpublished Changes?" (Restore This Version / Keep Editing; `confirmRestoreOverDraft()` in each page's dialog service), so a restore never silently replaces work in progress.
- A version is read through the page's current schema (`NavSettingsSchema`, `homeSettingsFromVersion()` with `HomeSettingsSchema`); one that no longer parses shows "Can't restore this version". The last row, "Built-in starting version" (shown even when the list can't load), asks first (**Restore and Publish**) and publishes straight away, like the old Reset to Defaults.
- Home Page publish and the built-in reset no longer delete the photos that were live before (only this session's unused uploads), because a previous version may still show them.

## Brands page

- **Brands page (`/brands`, `BrandsComponent`, <KEY>-230):** server-rendered (`RenderMode.Server`, `private, no-store`), so a Navigation edit shows on the next request.
- The Brands page lists only the Brands menu from `NavService.storefrontCategories()` (the saved Navigation, or the built-in `NAV_CATEGORIES` when `settings/navigation` has no categories); the page itself has no brand list of its own.
- The Brands page shows `<app-skeleton>` cards until `NavService.navLinksReady()`, then "Brands are coming soon." with **Shop All** (`/shop`) when there is no Brands menu.
- The Brands page count line is plain text ("12 brands", "1 brand"), counts each brand link once, and is hidden while loading or empty.

## Navigation links and auto columns

- **Navigation link targets (<KEY>-246)**: each menu and link in `settings/navigation` can save a `target` (`category` id, `brand` id, `page` `shop` / `sale` / `new-arrivals` / `brands`, `shop` filters, or a typed `url`); `path` is still saved next to it, built from the target at save, so the category page, Brands page, footer and server seed keep reading `path`, and older links without `target` work unchanged.
- One pure function builds the address: `resolveNavTarget()` / `navTargetPath()` in `src/app/core/services/navigation/nav-target.ts` (category → `/category/<slug>`, brand → `/brand/<slug>`, pages → `/shop`, `/shop?onSale=1`, `/shop?newArrivals=1`, `/brands`, Shop filters → `/shop?…` with Shop's query names and the brand's name for `brand`).
- `NavService.storefrontCategories` rebuilds addresses from targets with the published categories and brands (`resolveStorefrontTargets()`) and leaves out a link whose category or brand is hidden or gone (a menu with no links left goes too); on the server and until both lists load it uses the saved `path`, so the server HTML and the first browser render match.
- Admin → Navigation uses **Links To** (`app-nav-target-field`) instead of a typed address: categories, brands, pages, running offers, **Shop with Filters…** and **Outside Link**; menus also offer **Only Opens the Menu** (no target, no path).
- **Nothing on our store is typed (<KEY>-267)**: "Advanced: Type an Address" and ✨ are gone; **Outside Link** (target `url`) is the only typed choice and takes only a full `https://` address on another site (`outsideLinkProblem()` in `nav-target.ts`; our own addresses, atteyastore.com and the store's hosted.app hosts (`isOwnSiteHost()`), answer "Pick it from the list instead.").
- Offer targets (`{ kind: 'offer', id }` → `/shop?offer=<id>`) list the running public offers Shop can filter on (`NavigationCatalogService.runningOffers`: `liveOffers` signed out + `canShopOffer`); an offer link whose offer stopped running blocks Save ("isn't running now").
- An old link (address only, or a typed `url` on our site) opens as the target its address names (`effectiveNavTarget()` / `navTargetFromPath()`: category and sub-category, brand, pages, `/shop?offer=…`, Shop filters, `/category/<top>?…` as Shop with filters, our own full `https://` address); one that can't be matched shows "Pick where this goes." and blocks Save until picked; Save writes the matched target (`targetAndPath()` in `navigation-targets.utils.ts`).
- Outside Links show in mega-menu columns only (desktop and phone menus open them in a new tab, `isOutsideAddress()`); a top menu name has no Outside Link (`allowOutside` false) and Save refuses one; the category page pills and the Brands page leave them out.
- Save lists every problem and refuses a link or menu whose category or brand no longer exists, a link with no target and no address, an address that can't be matched or a bad Outside Link (`validateNavigationDraft()` in `navigation-manager.validator.ts`); a hidden target saves with a warning.
- **Columns that fill themselves (<KEY>-247)**: a mega-menu column can save `auto` (`NavAutoColumnSchema` in `src/app/core/services/navigation/nav-auto-columns.ts`): `{ kind: 'brands', limit? }` (shown brands in their Categories & Brands order), `{ kind: 'newest-brands', limit }` (newest by `createdAt`) or `{ kind: 'children', categoryId }` (that category's shown sub-categories, in order, at most 20); "Show at most" is 1–20, default 8.
- An auto column shows its links instead of the saved `links` (`expandAutoColumns()` / `navAutoColumnLinks()`, pure, tested by `npm run test:cart`): the same link shape as a picked target (`target` brand or category, `/brand/<slug>` / `/category/<slug>`), empty brands and categories (`CatalogService.isEmpty`) left out before the limit; `resolveStorefrontTargets()` and `visibleStorefrontCategories()` then run on them like any link.
- The column's own `links` stay saved while `auto` is on, so turning Fill Automatically off brings them back.
- "Brands in …" (brands with products in one category) is not built: it would need an Algolia facet read on every page render.
- `NavService.expandedCategories` is the saved navigation with auto columns turned into links (no hiding); `storefrontCategories` builds on it, and the category page and Home Page's import from the menu read it; the Brands page reads `directoryCategories` (the same, ignoring "Show at most", so it lists every brand).
- A "Sub-categories of …" column whose category is hidden or deleted shows nothing; `navLinksReady` waits for the brands when the saved navigation has a brand auto column (`NavAutoBrandsService.ready()`), so a client-rendered page never pops a brand column in.
- Sources: sub-categories come from `ShopCategoriesService.categories()` (server-seeded `shop-categories`, then live); brands from `NavAutoBrandsService` (`nav-auto-brands.service.ts`): `navigationSettingsResolver` reads the published brands on the server only when the saved navigation has a brand auto column (`navNeedsBrands()`), seeds them through TransferState (`nav-auto-brands`, a failed or slow (3 s) read gives no brands and `private, no-store`), and the browser follows `CatalogService.brands()` once it loads, so the server menu and the first browser render match.
- Admin → Navigation: each column has **Fill Automatically** (off by default), then **Fill With** (All Brands, Newest Brands, Sub-categories of …), **Category** (top-level, hidden ones marked) or **Show at most**; while on, the column's links and Add Link are hidden and "What the store shows now" previews the links (`NavigationDraftService.autoPreview()`, from `NavigationCatalogService.autoSources()`); Save refuses a "Sub-categories of …" column whose category no longer exists and warns when it is hidden.

## Home Page and motion

- `app-navigation-list-section` hides, for shoppers, a saved link whose category or brand has nothing published (`CatalogService.isEmpty(item.link)`, the check the menus use; links stay visible while `settings/catalog` counts are missing or loading, and the SSR seed matches the first client render). The admin preview (`previewMode`) and the saved `settings/home.navList` still hold every link.
- The server HTML marks the first link active. Photos mount only after the browser confirms the desktop layout, so a phone never requests them. Once that panel is up, CSS shows the first photo until GSAP runs. `prefers-reduced-motion` swaps instantly with no scale. A photo that is still downloading is not shown until it loads (1.2 s at most); the current photo stays meanwhile. The desktop arrow after the active name (`arrow_right_alt`, `size="4xl"`, `weight="700"`) follows the active row straight away (no wait for the photo), one arrow at a time: the previous one fades out in place, then the new one slides in from the left while it fades in; reduced motion shows it with no slide. See `reusable-catalog` for the inputs, the `settings/home.navList` field, and the `.nav-list*` classes.
- **Home row scroll lock** (`RowScrollLockDirective`, `src/app/features/home/directives/`, on the New Arrivals and Padel `.scroll-row`): on desktop (`min-width: 1024px`, hover + fine pointer, motion allowed) the section stays in place from the moment its bottom edge reaches the bottom of the window, and page scrolling moves through the cards (GSAP ScrollTrigger in `gsap.matchMedia`, scrub via `onUpdate`; `gsap` + `gsap/ScrollTrigger` loaded in `afterNextRender`, reverted on destroy). After the last card the page carries on; scrolling up does the same in reverse. The lock is CSS `position: sticky` plus a spacer after the section, not ScrollTrigger's fixed pin, because `<main>` is an `@container` (the containing block for `position: fixed`). New Arrivals is taller than a laptop window, so its row sets `rowLockFit=".product-card__media"`: the directive measures the rest of the section and sets `--row-lock-media-max` on it, which caps the photo height so heading, cards and arrows fit below the nav. A section that still doesn't fit (photos would go under 160 px), or a row that can't scroll, doesn't lock. Phones, tablets and reduced motion never lock. These rows set `[enableWheel]="false"` on `appHorizontalScroll`, so the wheel always scrolls the page; arrows go through `lock.step()` (scrolls the page while locked), and a drag or sideways swipe while locked moves the page with the row. If the row was moved while the page was outside the lock, entering the lock moves the page to match the row instead of jumping the cards. Snapping is turned off only on rows that actually lock.
- `/` is server-rendered (`RenderMode.Server`, `Cache-Control: private, no-store`) so a banner edit is on the next request and the HTML is not CDN-cached. `homeSettingsResolver` reads `settings/home` once with `getDoc` on the same client Firestore path as the product page (no App Check token; App Check is browser-only). The seed goes through `TransferState` (`home-settings`). The browser paints that seed, then `HomeService` attaches `onSnapshot`. A failed server read renders the built-in defaults and sets `Cache-Control: private, no-store`. The hero image overlay stays off while that seed is already showing. `priority` stays on slide 0 only.
- **Home Page links (<KEY>-267)**: hero buttons (Add/Edit Action Button dialog), shop cards and the category list use the same **Links To** picker (`app-nav-target-field`; the category list has no Outside Link) and save a `target` next to `link` / `buttonLink` (`target` in `home.schema.ts`), the address built from it at Publish (`homeWithTargets()` in `home-manager/utils/home-link-targets.utils.ts`, with `targetAndPath()` from Navigation); Publish refuses a link that can't be matched, a gone category or brand, an offer that isn't running or a bad Outside Link (`homeLinkProblem()`).
- The storefront home reads `HomeService.storefrontHero` / `storefrontShopCategories` / `storefrontNavList`: each link built from its target with the published categories and brands (`NavService.targetCatalog`, null on the server and until both lists load, when the saved address is used, like the menus; `features/home/utils/home-link-targets.utils.ts`), so a renamed category's button follows it; a hidden or deleted target's hero button and category-list row are left out and its shop card opens Shop All; links saved before targets keep their address; Outside Links on hero buttons and shop cards open in a new tab.
- Home saved copies (<KEY>-231): `HomeService` reads the hero, shop cards and category list it saved in `localStorage` once, through `v.safeParse()` with the `home.schema.ts` schemas (a broken copy is removed; ignored when the server sent its own seed, so hydration matches), and saves them only in the `onSnapshot` callback, never in a `computed()` (a section the live doc no longer has is removed). On a client navigation to `/`, `homeSettingsResolver` waits for `HomeService.whenReady()` (server seed, a saved hero, or the first snapshot; at most 3 seconds), so the built-in `DEFAULT_HOME_*` sections never flash before the real ones.

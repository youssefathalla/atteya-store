# Linear Board and Ticket Routine

Moved here word for word from AGENTS.md so that file stays small (<KEY>-282). The general Angular, Firebase and design rules stay in AGENTS.md.

**How to edit this file:** one fact per line, as a list item under the heading it belongs to. Add a new rule as its own line, or a new `##` heading for a new topic. Never join rules into one long paragraph: Git merges line by line, so two PRs that touch the same long line conflict even when they change different sentences.

## Ticket-pickup routine

**Ticket-pickup routine (ticket → PR without a person).** A scheduled Claude Code cloud routine ("Atteya Store: pick up agent-ready ticket", claude.ai/code/routines, every hour, Opus 5.5, Linear connector only) builds tickets you queue. To queue one, put the label `agent-ready` on a **Todo** issue whose description says exactly what done looks like. A scheduled run is a dispatcher: it finds every `agent-ready` Todo whose Linear **blocked by** issues are all in QA, Done or Canceled, and starts one build run per ready ticket (highest priority, then oldest), at most 4 `agent` tickets **In Progress** or **To Review** at once (a ticket whose PR is a draft or is stuck waiting for a person, with a 🛑 Claude Fix comment or a ✋ / "needs a person" comment on its latest commit, does not hold a slot and is listed as stuck; ⏳ comments mean the loop is still working); tickets still waiting on a blocker are started by a later run once it merges. Dependencies and tickets that edit the same files are linked as "blocked by", so they never run at the same time. If a run cannot start other runs, it builds the first ready ticket itself. That is the case today: an agent session may only start routines an agent created, and this one was created through the API, so each scheduled run builds one ticket; `npm run agent:build` from a person's machine still starts several at once. A build run swaps `agent-ready` for `agent`, moves the issue to In Progress, and either (a) comments what's missing and moves it to **Blocked** or to **Backlog** + `Open Questions` when the ticket is unclear, needs a decision, a console change, a new secret, a live data migration, anything on production, or a `.github/` change (a normal dev deploy after merge is not a blocker: it builds the change and lists `fb:*:dev` in the PR), or (b) branches off `origin/develop`, builds it following this file, runs `npm run preflight`, `npm run test:cart`, the functions tests and the dev build, and opens a PR (`<KEY>-123 …`, first description line `Linear: [<KEY>-123](…)` linking to the issue; a draft if a check still fails) and moves the issue to **To Review** (a draft's issue goes to **Blocked** with what fails). From there the review → fix → merge loop takes over. It never deploys or merges. **Start it now instead of waiting:** `npm run agent:build -- <KEY>-51 <KEY>-52 …` (`scripts/agent-build.mjs`) starts the routine once per ticket through its API ("fire" with the message `Build <id>`), so each ticket gets its own cloud session at the same time, and prints each session's link (`--dry-run` previews the model, the routine and whether its token was found). **Pick the model per ticket (the Linear **Model** label group: `Opus`, `Sonnet`, `Haiku`; one per issue):** Opus is the default and the person is on the Max plan, so usage cost is not a factor; Sonnet and Haiku are picked only because they finish a clearly simple ticket faster. **Opus** (no flag; the scheduled routine, id `trig_01BzzGXbAheJgZo7kqRxGUh8`): any ticket that isn't clearly small, and always for money, security or data: offers and pricing, checkout and orders, Paymob, stock, Firestore/Storage rules, sign-in and admin guards, server rendering and hydration, data scripts, work across several areas, or a bug whose cause isn't known. **Sonnet** (`--sonnet`, routine `trig_01UwGVcKtQkxrepBwEZEzcJ3`): a simple, clearly described change in one area where Opus would be slow for no gain: a small UI change in one component, a bug with a known cause, a small script or check; never money, security or data. **Haiku** (`--haiku`, routine `trig_01PWLhc1Yzys3h3sKHd1bkmT`): a tiny change in 1–2 files where the ticket gives the exact text or value: copy, one CSS value, docs, one setting; no logic, data, pricing or rules. When unsure, use Opus. Effort stays high on all three (`.claude/settings.json`). The hourly scheduled runs always build on Opus whatever the label (a scheduled run can't start the other routines). A ticket whose Sonnet or Haiku run ends as a draft, gets a 🛑 Claude Fix comment, or goes to **Blocked** because a check fails is relabelled one step up (Haiku → Sonnet → Opus) and started again. Passing both flags stops and starts nothing, and each started line names its model (`✓ <KEY>-90 (Sonnet): Claude started → <link>`). The Sonnet and Haiku routines use the same prompt and have no real schedule (a one-off 2099 date because claude.ai requires one), so they only run when started this way. Anyone can run it: the person in a terminal, Cursor, or Claude Code, which is how a Cursor session puts Claude to work right away. An on-demand run reads only the first ticket id from that message (untrusted), builds that issue if it is in **Todo**, **Backlog** or **Bugs** (no `agent-ready` needed, no waiting on other `agent` tickets), and stops if it is already further along. On-demand runs also refuse a ticket whose blockers are not yet in QA, Done or Canceled; they move it to Todo with `agent-ready` and comment what it waits on, so a later scheduled run starts it. Tickets started together can edit the same files; the first one to merge wins and a later one gets a merge conflict. **Conflicts are fixed automatically:** `.github/workflows/conflict-watch.yml` ("Conflict Watch / Fix Conflicting PRs", on when the repo variable `CONFLICT_FIX` is `enabled`) runs after every push to `develop` (and is started by `auto-merge.yml` after each of its merges, since those start no push workflows) and when an owner's PR into `develop` is opened, reopened, marked ready or gets a new push (`pull_request_target`, because GitHub runs no `pull_request` workflow while a PR conflicts; it never checks out PR code), so a PR that conflicts from the start is caught at once, finds open owner PRs into `develop` that conflict (not drafts, forks or `no-auto-merge`), and starts the routine with the message `Fix conflicts` using the repo secret `ATTEYA_ROUTINE_TOKEN_OPUS` (the same routine token; it can only start this routine). It comments **🔀 Conflict Fix** · started on each PR, once per PR head and `develop` commit. That run (step C of the routine prompt; scheduled runs also do it first, as a fallback) merges `develop` into each branch, keeps both sides of every conflict (`develop`'s side is never dropped; lock files are regenerated), runs the same checks as a build, and pushes as the repo owner, so CI, the Claude review and auto-merge carry on. It never touches a conflict under `.github/`, `.env*` or secrets, and when it can't resolve something safely or a check fails it pushes nothing and comments **🔀 Conflict Fix** · needs a person (PR and Linear) with the head commit; Conflict Watch then leaves that head alone. When the routine can't be started, Conflict Watch says "not started" once per PR head and reason, not on every push. After a change under `.github/workflows/` lands on `develop`, merging `develop` into an older branch may need a workflow permission the routine's push doesn't have, so expect those conflict fixes to come back as "needs a person": click Update branch on the PR or resolve them by hand. Each routine has its own API token, and a token only starts its own routine. The tokens live **outside the repo**: Windows user environment variables `ATTEYA_ROUTINE_TOKEN_OPUS` (Opus), `ATTEYA_ROUTINE_TOKEN_SONNET` and `ATTEYA_ROUTINE_TOKEN_HAIKU` (or the files `routine-token`, `routine-token-sonnet` and `routine-token-haiku` in `%USERPROFILE%\.atteya-store\`), each created on its routine's page (Edit → Trigger → API → Generate token, shown once; a new token revokes the old one, so for the Opus routine also update the `ATTEYA_ROUTINE_TOKEN_OPUS` repo secret, or Conflict Watch, which only starts the Opus routine, can no longer start it). A missing token prints the one-time setup steps for that routine. Never commit a token or print it. Limits: 30 starts per hour per routine, 100 per account. The prompt's source is `.claude/routines/ticket-pickup.md`: each routine's own prompt (Opus, Sonnet and Haiku) only tells it to read that file from `origin/develop` and follow it, so a change to the file reaches all three once it is merged into `develop`, with no routine to update by hand (set up Nov 11, 2026, <KEY>-176). `.claude/settings.json` sets Opus 5.5, Sonnet 5.5 and Haiku 5.5 to `effortLevel: "high"` (per-model `modelSettings`), which the routine's cloud sessions load from the repo, so local sessions in this project start at high effort too. Linear's team pull request automations (set Nov 7, 2026) do the status moves: draft PR open → **In Progress**, PR open or review activity → **To Review**, PR merge → **QA** (not Done; a person checks it on dev, then moves it to Done).

## Self-review before the push

**Self-review before the push (<KEY>-176).** Every routine build runs Claude Code's `/code-review` (`high` for money, stock, sign-in, rules, `functions/` or checkout; `medium` otherwise) and `/security-review` on its branch after the checks pass and before it pushes, fixes the high and medium findings, runs the checks again, and lists the result in a "Self-review" section of the PR body (step 4.5 of `.claude/routines/ticket-pickup.md`; `git remote set-head origin develop` first, or `/security-review` can't find the base). A conflict fix does the same when it resolved code by hand.

## Writing tickets

**Writing tickets (every agent that creates a Linear issue).** The person usually asks an agent to create tasks instead of writing them by hand, so every issue an agent creates in this project uses the "Agent ticket" format (also a Linear template with that name). Write the description as these Markdown sections, filled with real content, never hint text: `## What` (one or two sentences: the change and who it is for: shopper, admin or staff), `## Done when` (a `- [ ]` checklist of what to see on the dev site, including phone and desktop when it is UI), `## Where` (pages, admin screens, files or functions), `## Not in scope` (what must not change), `## Decisions already made` (exact wording, prices, colours, behaviour; write "None needed" when there are none), and optionally `## Notes`. When a ticket needs another one merged first, or edits the same files as another queued ticket, link it in Linear as **blocked by** that ticket (not only in the text): the routine reads those links to decide what can run in parallel. Set team and project from `linear.config.json`, status **Todo** (a bug: label `Bug`, status **Bugs**), and exactly one type label: `Bug`, `Feature` or `Improvement`. Every ticket also gets exactly one label from the **Model** group (`Opus`, `Sonnet` or `Haiku`), chosen with the rules in **Ticket-pickup routine** above (Opus by default; when unsure, Opus). Add `agent-ready` only when the person asks for it to be built automatically ("queue it", "let the agent build it") **and** every section is filled with no open decision. If something is undecided, create it without `agent-ready`, add `Open Questions`, put it in **Backlog**, and list the questions in the description and in your reply. When the person asks for tickets to be built **now** ("start Claude on these", "build them now"), create them as above, then run `npm run agent:build -- <id> <id> …` with the flag that matches each ticket's Model label (no flag for `Opus`, `--sonnet`, `--haiku`; one command per model when the tickets have different labels) and give the person the session links it prints. Leave those issues where they are (**Todo**, **Bugs** or **Backlog**), unassigned and not built in your own session: skip the board **Start** step for them, don't move them to **In Progress**, and don't branch or implement them yourself. Each cloud session claims its own ticket, and an on-demand run stops without building when its issue is already **In Progress** or further along.

## How to Test on Dev

**How to Test on Dev (<KEY>-87).** Every PR an agent opens (the ticket routine, Claude Code, Cursor, Antigravity) carries a ready-made QA checklist, so testing a ticket on dev takes about 5 minutes:
- The PR body has a `## How to Test on Dev` section; Claude Fix, conflict fixes and docs-only PRs are no exception (a docs-only PR says what to read or run instead).
- Its first line is the rough time to test: `About 5 minutes.` (a plain estimate, 2 to 15 minutes).
- Then `Setup:` with what must happen on dev first, one per line: the deploy step (`npm run fb:fn:dev`, `fb:rules:dev`, …), the data script with its exact command, Rebuild search, a test offer or test product to create, or a signed-in test account; `Setup: none` when there is nothing.
- Then 3 to 6 `- [ ]` steps, each one action and what you should see (`- [ ] Phone: open /shop?onSale=1 → only discounted products show`), saying "phone" or "desktop" where it matters and naming pages by their path.
- Steps a signed-out person can't check (admin pages, account, a real order) say so in the step (`Admin, signed in: …`).
- When the PR opens, the same section is added to the end of the Linear issue description (replacing an older `## How to Test on Dev` section there), so it is on the issue when it reaches **QA** and can be ticked in Linear on a phone; no GitHub workflow or Linear key is needed.
- If later commits on the PR (a fix round, review changes) change what to test, update both copies before the merge; the person who moves the issue to **QA** checks the issue's copy still matches what merged.

## Page Not Found, Something Went Wrong and catalog addresses

- **Page Not Found (<KEY>-268)**: any address the store doesn't know opens `NotFoundPage` (`features/errors/not-found.page.ts`), the last child (`**`) of the store layout, so the real menu and footer stay; it is server-rendered with HTTP 404, `noindex` and `private, no-store` (`app.routes.server.ts` `**`). `/admin` and `/playground` are listed before the store layout so that `**` never swallows them; an unknown `/admin/…` address also lands on Page Not Found.
- **Something Went Wrong (<KEY>-268)**: a store page whose code can't be downloaded (offline, an old tab after a release) is caught by `withNavigationErrorHandler` and `AppErrorHandler` (`@core/services/errors`, `isChunkLoadError()`) while a navigation is running; `PageLoadErrorService.failedUrl` makes `MainLayoutComponent` show `<app-error-page kind="failed">` in place of the page (the router outlet stays, hidden) until the next navigation starts (or one is cancelled or skipped); Try Again opens the failed address. A failed part of a page that is already showing never replaces the page.
- **Missing page code after a release (<KEY>-273)**: before showing Something Went Wrong, `PageLoadErrorService.report()` reloads the site once at the address that failed (`location.assign`), because a tab opened before a release asks for code files the new release no longer has; this covers `/admin` too, whose layout has no error page. It doesn't reload while offline, when `sessionStorage` is blocked, or within 30 seconds of the last such reload (`atteya-missing-code-reload`, `shouldReloadForMissingCode()` in `page-load-error.ts`, tested by `npm run test:cart`), so a file that is really missing shows the error instead of reloading in a loop.
- Both pages use `<app-error-page>` (`@shared/ui/error-page`): `kind` `not-found` (kicker ERROR 404, PAGE NOT FOUND, a search box that is a plain GET form to `/search`, Continue Shopping, Back to the Home Page) or `failed` (SOMETHING WENT WRONG, Try Again reloads, Back to the Home Page), plus the WhatsApp line when `contact.whatsapp` is set; no header, menu or footer of its own and no category buttons. The product page's missing product (404) and read error (503), and the category, brand, Shop and Search pages' failed-load branches show it too (`[level]="2"` where the page already has an `h1`). Server status helpers: `markNotFound()` in `@shared/utils/error-response`.
- **Category and brand addresses never open empty (<KEY>-268)**: `catalogPageResolver` (`features/category/resolvers/`, on `category/:slug` (both routes), `category/:slug/:subSlug`, `category/accessories/bags` and `brand/:slug`; pure rules `decideCategoryPage()` / `decideBrandPage()` in `features/category/utils/catalog-page-state.ts`, tested by `npm run test:cart`) runs after the store layout's resolvers and uses the `settings/catalog` counts, the published categories (`ShopCategoriesService`) and, for brands, the live brand list or one `brands` read (`published == true`, `slug ==`, limit 1, 3 s).
- An empty (0 live products) or hidden sub-category goes to its main category (its parent; `/category/apparel/hoodies` → `/category/apparel`, or `/shop` when that is empty or hidden too); an empty or hidden main category or brand (the built-in Apparel, Accessories and Rackets too) goes to `/shop`: a 302 with `private, no-store` on the server (302, not 301, because it comes back once products are live), `RedirectCommand` with `replaceUrl` in the browser.
- A deleted or unknown category or brand (no count key in `settings/catalog`, or a deleted built-in), or a sub-category address whose main category is gone, shows Page Not Found with 404 (`catalogPage` input on `CategoryComponent`); the Shop routes never answer 404 (a category with no count yet opens as before). Without counts, while the built-in category list stands in for a failed read (`ShopCategoriesService.isRealList()`), or when the brand read fails, nothing is decided and the page opens as before. Brands are read by slug (brand ids are their slugs; the live list in the browser matches either). A hidden category or brand whose id differs from its slug looks deleted (counts are keyed by id) and gets 404. `/category/all`, `/category/sale` and the merchandising sub-pages are left alone.

## Store layout

- **`ShellReadyService`** (`@core/services/shell/`): `ready()` is true when `CurrencyService.ready()`, `ShippingSettingsService.shellReady()`, `BannerOffersService.shellReady()`, `NavService.shellReady()` (SSR seed or first live doc), and browser `AuthService.isAuthReady()` (SSR skips Firebase auth). **`chromeReady()`** is currency + shipping + banner offers + navigation. **`MainLayoutComponent`** shows a one-time `<app-loader>` overlay until `chromeReady()` on the first storefront load (not on every navigation; route changes keep the top pulse only). The announcement bar mounts only when `chromeReady()` so EGP copy and banner offers do not pop in; SSR HTML still carries route body for LCP. Account menu keeps its own `isAuthReady()` gate.
- **Announcement bar (`app-announcement-bar`, `src/app/layout/announcement-bar/`, <KEY>-145):** the one slim black bar (`h-9`, same on phone and desktop; `.announcement-bar*` in `announcement-bar.css`) above the navigation, replacing the old shipping banner; not on focus pages and no close button. Slides, in order: up to 4 offers staff put in the top banner (`bannerOffers()` in `@core/services/offers/offer-shop`: `banner.show`, `canShopOffer()` (public, for everyone, no code, no per-customer limit), running now, `offerTitleVisible()` so no Free shipping slide outside Egypt; highest priority, then newest edit), then the shipping message (`ShippingSettingsService.bannerText()`, EGP visitors only). An offer slide is a link to `/shop?offer=<id>` with `bannerText()` (the banner text, or the customer title) and `bannerCountdown()` ("· Ends in 2d 14h 05m", under 24 hours "· Ends in 05:12:33", `tabular-nums`; Hide / Always / only in the last N days); the shipping slide is not a link. Two or more slides fade every 5 seconds (all slides share one grid cell, so the height never changes), pausing on hover, keyboard focus and touch; ‹ › native buttons on desktop ("Previous announcement" / "Next announcement"; the icon font has only `chevron_right`, so Previous is mirrored), swipe on phone, `prefers-reduced-motion` = no auto-rotation and no fade; `aria-label="Announcements"`, `aria-live` off while rotating. Data: `BannerOffersService` (`@core/services/offers/banner-offers.service.ts`) uses the `banner-offers` TransferState seed from `bannerOffersResolver` (main layout; server only: `active`, `visibility == 'public'`, `banner.show == true`, limit 20, each doc `safeParse`d), then `OffersService.all()` once its listener answers, so a paused, archived or ended offer leaves live (a 1-second clock runs only while a banner offer has a start or end time). While `html[data-cur-pending]` is set, the shipping slide (and a bar holding only it, `data-shipping-only`) is hidden.
- **Footer (`app-footer`, `src/app/layout/footer/`):** rendered by `MainLayoutComponent` inside `@defer (hydrate on viewport)` and left out on focus pages. Columns: Shop (Shop All, `NavService.storefrontCategories()` minus `/shop` and `/brands`, Brands), Help (Message Us on WhatsApp, only when `contact.whatsapp` is set), Account (Sign In / Create Account when signed out, Favorites, Admin Dashboard for admins, Sign Out when signed in; neither shows on the server or before `isAuthReady()`, so hydration matches). Bottom row: `© Atteya Store <year>`, Terms, Privacy, and social icons (`footerSocialLinks()`: Facebook, Instagram, TikTok, WhatsApp; an empty `https://` link in `store-info.ts` hides that icon; inline Simple Icons SVG paths, CC0). The email sign-up (`app-footer-signup`) sits at the top of the footer, full width (the email field and a **Subscribe** button, full width on phone, side by side from `sm` capped at `max-w-xl`, then "By subscribing, you agree to our Privacy Policy. You can unsubscribe at any time." linking to `/privacy`), with the link columns under it; it shows to everyone except a signed-in shopper (the server and the first browser render show it, so hydration matches and the columns never jump down for a visitor). It calls the open `subscribeToEmails` callable (`europe-west3`, no sign-in, `requireAppCheck`; `functions/src/marketing/`), which stores `emailSignups/{sha256(lowercased email)}` once (`email`, `source: 'footer'`, `page`, `uid`, `createdAt`); a repeat returns `already-subscribed` and changes nothing. Each caller IP (hashed, never stored) gets 10 tries per UTC day, and the whole store 500 (`all_{day}`), both in `emailSignupRateLimits` with an `expireAt` 2 days later for a Firestore TTL policy (the IP can be faked, so the store-wide cap is what bounds a script; reaching it logs an error, and real visitors are refused until UTC midnight, so turn on App Check enforcement if that happens). Rules deny every client read and write on both collections. Nothing sends to the list yet; signed-in shoppers will manage emails in their account (<KEY>-51).
- **Shopper account (`/account`, `src/app/features/account/`; account panel `app-account-panel`, `src/app/layout/account-panel/`):** the signed-in account icon opens the account panel through `AccountPanelService` (CDK `Dialog`, lazy-loaded, same `.side-panel` shell as search: 28rem from the right on `lg`, full screen on phone; any navigation closes it). It shows the first letter of the name in a circle, name and email, **Complete Your Profile** while `users/{uid}` has no name or phone (`isProfileIncomplete()`), links to Account, Orders (`/account#orders`) and Favorites, a Latest Order card and a Favorites card (each with **Start Shopping** when empty), "Need help? Message Us on WhatsApp" (only when `contact.whatsapp` is set); **Sign Out** is the last row of the link list (a native button styled as `.account-panel__link`), not a button in a bottom bar. `/account` is client-rendered (`RenderMode.Client`, `private, no-store`) behind `accountAuthGuard`, laid out as a dashboard (<KEY>-214): a black welcome bar (first letter, "Hi, <name>", email, order count from `ShopperOrdersService.count()` and favorites count, a native **Sign Out** button), then a grid (`.account-grid`): three columns from the `@6xl` container width (Orders, then Delivery Address, then Profile, Favorites and Emails), two from `@3xl` (Orders on the left, Address above the rest on the right), one below; Orders shows the newest order as a large card with up to 4 photos and a Placed → Confirmed → Shipped → Delivered bar, then Earlier Orders; the sections: Profile (name required, phone optional; an Egyptian number must be a WhatsApp mobile, others need `+`/`00` and the country code; email read-only; **Save Changes**), Delivery Address (one address, `users/{uid}.address`, same fields checkout uses for that country), Emails (offers and new arrivals on/off, writes `marketingOptIn` + `marketingOptInAt`), Orders (live, newest first, 20 at a time with **Show More Orders**; ref, date, items, total in EGP, status name; each opens `/checkout/confirmation/:orderId`). `UserProfileService` (`watch`, `saveDetails`, `saveAddress`, `setMarketingOptIn`) writes with `updateDoc`; `ShopperOrdersService.watch(uid, max)` lists `orders` where `customerId == uid` ordered by `createdAt` desc (existing owner-list rule and index). Status names come from `orderStatusName()` (`@core/services/orders/order-status-name.ts`), shared with the confirmation page. Checkout reads the saved address once and fills the form when its country matches the delivery country and the shopper hasn't typed an address yet; checkout never saves over it.
- **Shopping bag (`app-cart-drawer`, `src/app/layout/cart-drawer/`):** an 840px `mat-drawer` (at most the window width minus 64px) from the right on desktop (`lg`; width set in `_sidenav.scss` for `app-main-layout`) and a full-screen slide-up panel on phone, both opened through `DrawerService` (`'cart'`). It is mounted twice (`placement="side"` in `MainLayoutComponent`, `placement="sheet"` in the mobile bar); only the phone copy shows and loads recommendations (the desktop side bag has no Recommended row). Both copies carry `ngSkipHydration`: the server never has the saved bag, so its HTML is always the empty bag, and hydrating it after `CartService` read `localStorage` left "Your bag is empty" above the items. Heading **Your Bag (n items)** (n = pieces). Each item is a bordered card (`.bag-card`): photo, name with the bin button (`Remove <name>`) at the top right, one quiet options line under the name (`optionsLine()`: "Size M · Black", size first with its label, gender last and only when the name does not say it; one line, long lists end in "…"), a square − / + box (− stops at 1) and the line price at the bottom right (old price struck through above it). Under the body: each free gift as its own row (small photo, name, "Free"), Buy X Get Y nudges (a dashed strip "Add 1 more to get 1 free" with an **Add 1** button when the free pieces come from the same items; the free-pick tiles under a dashed line otherwise) and grey offer strips from `lineStrips()` (the per-item offer with its percent off and "You save", each Buy X Get Y offer with its `.deal-tag`, the free-gift offer with "n free gifts"). A product that is no longer available keeps a greyed card ("No longer available") with only the bin. Under the items: **Payment Methods** (`bagPaymentMethods()` in `layout/cart-drawer/utils/bag-extras.ts`: InstaPay, Card and Cash on Delivery in Egypt, Card abroad, decided by `CurrencyService.visitorCountry()` with Egypt as the fallback; Card shows "Coming soon" and comes last while `isCardOrWalletLive()` is false), a compact list with one short row per method (`.bag-pay-row`, <KEY>-121): the method's mark in a small 52×32 box (InstaPay logo about 18px tall, icons 20px), then the name (14px); on a phone the rows stack, split by a light line, and from `sm` (tablet sheet, desktop side bag) all three sit on one line (`.bag-pay-list`); Card while it is coming soon keeps the same solid mark box border as the others, with its icons, name and "Coming soon" (12px, muted; on the right of the row on a phone) at 40% opacity. The same list shows in the desktop side bag and the phone bag. Payment method marks (bag, checkout, order confirmation) all come from `app-payment-mark` (`@shared/ui/payment-mark`, names and marks in `PAYMENT_METHODS`; logo file `public/img/payments/instapay.png`), then, on phone only, **Recommended for You**: up to 4 product cards from `SearchService.browseCatalog` filtered to the bag's main categories and `inStock:true`, products already in the bag left out, hidden when there are none. Two cards plus a peek; mouse drag, trackpad sideways swipe and finger swipe move the row and settle on a card, the wheel stays on the bag's own scroll, and the same arrows + progress line as the home rows (`app-row-scroll-nav`, `@shared/ui/row-scroll-nav`) sit under it only when it can scroll (`appHorizontalScroll` with `[trackScroll]="true"`, `exportAs: 'horizontalScroll'`; no scroll lock). No shipping fee in the bag; the footer says "Shipping is worked out at checkout." The empty bag shows a short message and **Start Shopping** (`/shop`) with no footer. Only the middle part scrolls (`overscroll-contain`); the header and the Subtotal / Checkout footer stay in place. While the bag is open `DrawerService` locks the page behind with the CDK block scroll strategy (same lock as the CDK Dialog panels, iOS Safari included), and closing puts the page back where it was.
- **Bundle & Save page (`/bundle/<offer id>`, <KEY>-279):** one page per Bundle & Save offer (`src/app/features/bundle/`, server-rendered with `private, no-store`, `noindex`; a missing offer or another kind of offer answers 404 with Page Not Found) where the shopper picks one product (and size) from each group and adds the whole bundle with **Add Bundle to Bag**; every link to a Bundle & Save offer goes there through `bundleOfferLink()` (`@core/services/offers/offer-shop`). Full rules: the `offers` skill, "Bundle & Save page".
- **Product grid first row (photos):** Shop / category (`app-shop-grid`) and Firestore category / brand (`app-catalog-product-grid`) give `priority` to exactly the first row on each screen through `injectFirstRowCount()` (`@shared/utils/first-row.utils`): 2 on phone, 3 on tablet, 4 on desktop (Shop: 3 from tablet up). The server always uses the phone row, so phones never preload the desktop row; the browser reads the width once when the grid is created and the extra desktop photos switch to eager loading on hydration; this clears the NG02955 note on `/category/rackets`.
- **Search panel (`app-search-panel`, `src/app/layout/search-panel/`):** the navbar and mobile-bar search icons and the phone menu's search row (a native button, `searchRequested` on `app-mobile-menu`; focus returns to the menu button) open quick search over the current page through `SearchPanelService` (CDK `Dialog`, component lazy-loaded on first open): a 28rem side panel from the right on desktop (`lg`), full screen on phone. Up to 6 matches from 2 letters, priced with `searchHitCardPrice()` in the visitor's currency; Enter or **See All Results** opens `/search?q=…`, which stays the full server-rendered results page. Esc, the close button, a click outside or any navigation closes it, and focus returns to the icon.
- **Closed phone panels are inert (<KEY>-227):** the phone menu (`app-mobile-menu`), the phone bag sheet and Shop's Filters panel stay in the page off screen when closed, so they carry `[attr.inert]` and `aria-hidden="true"` only while closed (no `aria-hidden` while open), and Tab never reaches their links.
- **Focus chrome (single-task pages):** routes with `data: FOCUS_CHROME` (`layout/main/chrome-mode.ts`; today `/login` and `/checkout`) stay inside `MainLayoutComponent` but show only a slim `h-14` bar with `<app-logo>` (links home): no shipping banner, navigation, footer or mobile bottom bar, and no first-load store loader (checkout waits for currency itself). `chromeModeOf()` reads the deepest active route, set from the router state at creation and on each `NavigationEnd`. The order confirmation page keeps the full store chrome.

## Manual shopper check

- Shopper check: home renders navigation from Firestore; `/shop` (and every top-level category's `/category/<slug>` plus Bags) browse Algolia with Show/Hide filters (Multi colour via `app-color-swatch`); `/search` queries Algolia; a result opens `/product/:slug` with an EGP price. `/brand/:slug` still lists from Firestore. `/category/all` and `/category/shop` redirect to `/shop`. Merchandising-only paths (`sale`, `…/new`, `…/best-sellers`) show an empty state until dedicated filters exist, so navigation never links them: the built-in menu (`nav.data.ts`) links only shop routes, published category and brand pages, `/brands`, and shop filters the page reads (Sale is `/shop?onSale=1`; New arrivals is `/shop?newArrivals=1`; the home New Arrivals title opens it when the row has marked new arrivals, and `/shop?sort=newest` when the row is filled only with the newest products). Saved link strings go through the `linkTarget` pipe so a `?query` reaches the router as a query.

# CI and Review Loop

Moved here word for word from AGENTS.md so that file stays small (<KEY>-282). The general Angular, Firebase and design rules stay in AGENTS.md.

**How to edit this file:** one fact per line, as a list item under the heading it belongs to. Add a new rule as its own line, or a new `##` heading for a new topic. Never join rules into one long paragraph: Git merges line by line, so two PRs that touch the same long line conflict even when they change different sentences.

## Pre-push git hook

   **Pre-push git hook (every person and agent).** `npm ci` / `npm install` run the `prepare` script (`scripts/hooks/install-git-hooks.mjs`, skipped on CI), which sets `core.hooksPath` to `scripts/git-hooks/`. On every `git push`, `scripts/git-hooks/pre-push` runs `scripts/hooks/pre-push.mjs`: it blocks a pushed branch whose name breaks the rule (with the exact `git branch -m` rename and old-branch delete commands), and new non-merge commits whose message doesn't start with `<KEY>-123` (`develop` and `main` exempt from both). Then it runs `npm run preflight` and `npm run test:cart`, plus `npm test --prefix functions` when `functions/` changed and `npx ng build --configuration development` when app code (`src/`, `public/`, `angular.json`, `package*.json`, `tsconfig*.json`) changed, compared with the remote branch or `origin/develop` for a new branch. A failure stops the push, so CI on GitHub (still the safety net for cloud and Cursor agents and auto-merge's proof) almost always passes first time. `SKIP_PUSH_CHECKS=1 git push` keeps the name and commit rules but skips build and tests; `git push --no-verify` skips everything, emergencies only and never by an agent unless the person asks. Before opening a PR, agents also review their own diff (`/code-review` and `/security-review` in Claude Code, Cursor's review) against `REVIEW.md`, the project review checklist that the Claude review reads too (see the **`preflight-gate`** skill).

## Review → fix → merge loop

- **Review → fix → merge loop** (PRs into `develop` opened by the repo owner): the Claude review (a code review and a security review of every push) is the only automated reviewer. Cursor Bugbot and the Cursor Security Agent are no longer used (<KEY>-85).
- `.github/workflows/claude-review.yml` (on when the repo variable `CLAUDE_REVIEW` is `enabled`) reviews every push and writes one verdict marker for both passes on its comment: `<!-- claude-review-verdict <sha> clean|issues|none -->`, plus the findings of both passes as base64 JSON in `<!-- claude-review-findings … -->` when there are issues. Only comments from `github-actions[bot]` count.
- `.github/workflows/bugbot-claude-fix.yml` ("Claude Fix", on when the repo variable `BUGBOT_CLAUDE_FIX` is `enabled`; the file name is kept) runs on each finished Claude Review (`workflow_run`) and has Claude fix its `high` and `medium` findings on the same branch with file tools only (ids `cr-<comment id>-<n>`; low ones stay notes and never hold a merge).
- Claude Fix can't edit the generated copies under `src/app/core/services/offers/engine/` and `src/app/core/config/`; the push hook copies `functions/src` over them the same way `npm run sync:engine` does, from its own root-owned copy of that script, before committing.
- A root-owned hook commits (`<KEY>-123 Fix Claude review findings from review …`, id taken from the PR title) and pushes. The push starts a new Claude review (the Claude step allows the `claude` bot, because a Claude Review of a Claude Fix commit starts the next round as `claude[bot]`), so the loop repeats until the review has no `high` or `medium` finding.
- After 3 rounds the workflow stops and comments **🛑 Claude Fix** that a person is needed.
- A round where Claude never ran (expired sign-in token or usage limit, the branch moved first) is rewritten to `<!-- bugbot-claude-void …` and does not count toward the cap.
- A PR that changes `bugbot-claude-fix.yml` gets one **✋ Claude Fix** comment and no round, because the Claude action refuses to run then.
- When a round pushes nothing and the branch is still on the reviewed commit, its report is titled **✋ Claude Fix** · nothing pushed, needs you, with what to do.
- Claude Fix runs one round at a time per PR; a failed Claude Review run uses its own concurrency group so it never pushes a waiting round out.
- Its "Claim a Fix Round" job starts only for a successful Claude Review run of a pull request; the verdict is only in the comment, not in the event, so a clean review still starts that job and the script stops it.
- `.github/workflows/auto-merge.yml` (on when `AUTO_MERGE` is `enabled`) squash-merges into `develop` and deletes the branch when, on the PR's latest commit, the "CI / Build and Test" and "PR Title / Linear ID in Title" checks passed (and "Browser Check / Phone and Desktop Pages" when it ran on that commit), nothing else failed or is still running, the Claude review has finished with no `high` or `medium` finding, there is no open review thread from a person, no "changes requested", and GitHub says the PR can merge.
- Checks from the Cursor app (old Bugbot or Security Agent runs) are ignored and never hold a merge; threads left by bots never hold it either.
- A Claude review with no result (failed, usage limit, or not run) holds with a **✋ Auto-merge** comment once per commit; a `high` or `medium` finding holds with **⏳ Auto-merge** (waiting for Claude Fix).
- Resolving a thread starts no workflow, so then run Actions → Auto-merge → Run workflow on `develop` with the PR number (only the repo owner, only from the default branch; other runs are skipped).
- Ticking `skip_claude_findings` on that run also skips the Claude review hold (a finding or no result), for when you decide it is fine, but never a failed check.
- Auto-merge never merges into `main`, and skips drafts, the `no-auto-merge` label, forks, and PRs that change `.github/` (those wait for a person).
- Its `workflow_run` trigger only runs the copy on the repository's default branch.
- Every started job bills at least a minute (a job skipped by its `if:` is free), so auto-merge's job starts only on an event that can be the last gate a clean PR waits for: CI, PR Title or Browser Check finishing with `success`, Claude Review finishing in any way but skipped (a review with no result holds with a note, so even a failed one can be last), or the hand-started run; never for forks or push runs.
- Its concurrency group is per commit at job level (skipped events never join it), a newer event replaces one still waiting, and a running check is never cancelled (it may be halfway through a merge).
- It lists every check run on the commit (`filter: 'all'`) and takes the newest of each name, except that a skipped "Linear ID in Title" never replaces a real one (PR Title skips its job when an edit leaves the title and base as they were).
- A merge made by the workflow token starts no other workflow, so CI does not re-run on that push to `develop`.
- **Auto-merge retries when `develop` moves (<KEY>-149).** A merge GitHub refuses with "Base branch was modified" (405 / 409, another PR merged a moment earlier) is retried up to 3 times, re-reading the PR each time; after the third refusal it posts **✋ Auto-merge** once per commit with how to start it again (Actions → Auto-merge → Run workflow).
- **Auto-merge checks the other PRs after a merge (<KEY>-149).** After any merge it checks every other open owner PR into `develop` once, quietly (no ✋ / ⏳ notes, except the ✋ note after three refused merges), and merges the clean ones, so a PR that lost the race needs no new event; It starts Conflict Watch right after the first merge (and once more if the check of other PRs merged more), and stops checking after 6 minutes so the 10-minute job timeout never cuts it off.
- **Claude Fix formats before it pushes (<KEY>-177).** The root-owned push hook runs Prettier on the code files Claude changed (before the engine copy, so generated copies match), using the lock file's Prettier version installed into `/opt/bugbot-guard` with install scripts off and a fixed copy of `.prettierrc` kept in `bugbot-claude-fix.yml` (change both together). No pull request code runs in that job. A file Prettier can't parse pushes nothing and reports **✋ Claude Fix** · nothing pushed with Prettier's error. Preflight, the build and the tests still run only in CI after the push, because running the repo's scripts next to the push token is unsafe.
- GitHub's "Automatically delete head branches" setting is **off** because it would also delete `develop` after a `develop` → `main` PR. `.github/workflows/delete-merged-branches.yml` deletes a merged PR's branch instead and always skips `develop` and `main`. A deleted branch can be restored from its PR page.

## Checks, Browser Check and Claude review

- **Check and comment names**: each check in a PR's list reads "workflow / job", named for what it does: "CI / Build and Test", "PR Title / Linear ID in Title", "Claude Review / Code Review", "Claude Review / Security Review" and "Claude Review / Post the Review", "Claude Fix / Claim a Fix Round" and "Claude Fix / Fix Review Findings", "Auto-merge / Merge When Clean", "Browser Check / Phone and Desktop Pages" and "Browser Check / Post the Result", "Claude Mentions / Answer @claude" (starts only when the comment or issue author is the owner, a member or a collaborator), "Delete Merged Branch / Delete Branch After Merge", "Conflict Watch / Fix Conflicting PRs" (runs on `develop`; PR events list it on the PR's commit too, and auto-merge ignores it there). A green check only means the job ran; the result is in its comment. Each bot comment starts with a title: **🤖 Claude Review**, **🔧 Claude Fix** (round started, then the report), **🛑 Claude Fix** (stopped after 3 rounds), **✅ Auto-merge** (merged), **✋ Auto-merge** (waiting for you), **⏳ Auto-merge** (waiting for Claude Fix; nothing for you yet), **✋ Claude Fix** (nothing pushed, or the PR changes Claude Fix's own workflow: needs you), **🖥 Browser Check** (pages passed, or which failed and why) or **🔀 Conflict Fix** (started, resolved, not started, or needs a person). All of them post as `github-actions[bot]` (that name can't be changed; the Claude action's own `claude[bot]` token is already cancelled when the comment step runs, so it can't be used to post). `auto-merge.yml` still accepts the old check names (`checks`, `linear-id`, `Claude Review (Trial)`) and the old "PR title" workflow name, for branches made before the rename.
- **Browser check (website PRs)**: `.github/workflows/browser-check.yml` ("Browser Check / Phone and Desktop Pages") runs on every push to an owner's non-draft PR into `develop` (a newer push cancels the older run) **only when the PR changes something the website build uses**: its `paths` allow-list is `src/**`, `public/**`, `angular.json`, `package.json`, `package-lock.json`, `tsconfig*.json`, `.postcssrc.json` (Tailwind), `.nvmrc`, `scripts/browser-check.mjs`, `.github/workflows/browser-check.yml` and `apphosting*.yaml` (GitHub reads the first 300 changed files for this). A PR that only changes `functions/` code, Firebase rules or indexes, docs or scripts has no Browser Check run (it tests the website against the live dev Cloud Functions, so it has nothing to check there), and auto-merge doesn't wait for one. Pricing-engine and store-info changes still start it, because `npm run sync:engine` copies them into `src/`. CI's own docs-only skip of its app build is separate. It builds the app (`ng build --configuration development`), starts the server-rendered store on the runner (`PORT=4000`, `NG_ALLOWED_HOSTS=localhost,127.0.0.1`) against live dev Firestore, Algolia and ImageKit through the public client config (no secrets), installs Playwright for that run only (`npm i --no-save playwright@1.63.0`; not a repo dependency) and runs `scripts/browser-check.mjs`. It opens home, `/shop`, `/category/rackets`, the first product Shop shows, `/search?q=<first word of that product>`, the bag with that product in it (seeded through `localStorage` `atteya-cart-v1`, opened with the visible "Shopping Cart" button) and `/login`, each at 390×844 (phone, touch) and 1440×900 (desktop). It opens `/checkout` signed out with that product in the bag (guest checkout) and needs its Email field. It also opens `/account`, `/favorites` and `/admin` signed out (never with an account or secrets; `SIGNED_OUT_PAGES` in the script): each must land on `/login` with `returnUrl` pointing back at that page (for `/admin`, a page inside `/admin`, because the guard runs after the child redirect), and one that opens instead fails with "<page> opened without signing in". The comment lists those three in one **Signed-out access** row. A page fails when its document answers 4xx/5xx or lands on another path (an unknown address must answer 404 with Page Not Found; the script opens `/this-page-does-not-exist` and checks exactly that), it throws, it logs a console error not in `ALLOWED_CONSOLE`, a request to our own server fails or answers 4xx/5xx, the store loader never goes away, the main area is empty or says it couldn't load, or what the page is for is missing (product cards on Shop and Search, the product name, the bag line, the email field). A failed page is tried once more. Outside files that don't load (photos, fonts) and Angular's dev-mode performance hints (`PERFORMANCE_HINTS`, such as NG02955: the largest photo has no `priority`) are listed as notes, not failures. That job runs the PR's own code, so it has a read-only token that checkout does not keep (`persist-credentials: false`); a second job, "Post the Result", runs no PR code, gets `pull-requests: write`, and posts the summary the first job saved. Screenshots go up as the `browser-check` artifact (14 days) and one **🖥 Browser Check** comment per commit (`<!-- browser-check <sha> -->`) lists pass/fail per page and size. Auto-merge requires it when it ran on the commit (older commits without a run are not held). Run it locally against a running store with `node scripts/browser-check.mjs --out browser-check` (`--product /product/<slug>` when Shop can't load; it uses `HTTPS_PROXY` for Chromium when set). Add a harmless console error to `ALLOWED_CONSOLE` with a comment saying why, never a broad pattern.
- **Browser Check install (<KEY>-208)**: the Chromium download retries 3 times and fails the job only after the third try; then Chromium is started once, and when it starts (the runner image already has its libraries) apt is never called, because Ubuntu's servers are sometimes unreachable from GitHub runners and apt then eats the job's 15 minutes; only when Chromium can't start does `playwright install-deps chromium` run (2 tries, 3 minutes each), and the step fails with Chromium's own error if it still can't start.
- **Claude review**: `.github/workflows/claude-review.yml` (on when the repo variable `CLAUDE_REVIEW` is `enabled`) reviews every push to an owner's non-draft PR into `develop` with Claude Opus on the Max plan (`CLAUDE_CODE_OAUTH_TOKEN`, so it shares the interactive usage limits).
- It uses read-only tools (`Read`, `Grep`, `Glob`, `git diff/log/show`) and loads no project settings or hooks from the PR checkout (`--setting-sources user`, so a PR cannot run its own hook scripts next to the Max token).
- Two passes run side by side on each commit: **Code Review** (bugs, broken project rules, security problems it sees) and **Security Review** (our own prompt based on Claude Code's `/security-review`: only exploitable vulnerabilities the diff introduces, more than 80% confidence, no DoS or theoretical issues; every finding has category `security`). Both use `--max-turns 40`, and a new push cancels the older run (per-PR concurrency).
- Both read the review criteria from the base branch with `git show origin/develop:<path>` (`REVIEW.md`, `AGENTS.md` and the matching skills), never from the PR's changes, so a PR cannot change what it is reviewed against. `REVIEW.md` (repo root, formerly `.cursor/BUGBOT.md`) is the short checklist of what breaks production, money, data or security here.
- **Post the Review** then posts one comment per commit (`<!-- claude-review-comment <sha> -->`) with a Code review and a Security review section, findings by severity (`high`/`medium`/`low`) and category (`bug`/`security`/`rule`).
- Verdict: `clean` when both passes finished with no findings; `issues` when both finished and one has findings, or one finished with a high or medium finding (so Claude Fix can start; its push reviews again); `none` when a pass has no result and nothing serious was found, which holds auto-merge with **✋ Auto-merge** (`skip_claude_findings` still overrides it). The hidden findings list holds both passes, most severe first, at most 20 (what Claude Fix reads).
- Auto-merge waits while any Claude Review job or run on the commit is still going.
- It never edits, fixes, resolves or merges, and its jobs always end green; its verdict marker is the review gate for auto-merge and the source of Claude Fix rounds (see the review loop above).

## Claude Code hooks and agents

- **Claude Code hooks and agents** (`.claude/settings.json`, `.claude/agents/`): a `PreToolUse` hook, `scripts/hooks/guard-generated-and-deploy.mjs`, blocks Edit/Write on a generated copy (the `.claude/skills/`, `.claude/rules/`, `.agents/rules/` and `.agents/workflows/` copies, the engine copy in `src/app/core/services/offers/engine/`, and the `src/app/core/config/` files copied from `functions/src/store/`) and names the source file plus `npm run sync:agents` or `npm run sync:engine`. It also blocks any Bash or PowerShell command that names the Firebase CLI and also has the word `deploy`, because deploys go through `npm run fb:*`. It does not read shell syntax at all, on purpose, and has no exceptions (not even heredocs). So text that only mentions a deploy is written to a file with the Write tool first (`git commit -F <file>`, `--body-file <file>`), and searches use the Grep tool. Subagents: `ticket-qa` checks one ticket's Done-when list on the dev site, on phone and desktop. It never signs in, and anything that needs an account comes back as needs-person. `money-path-reviewer` reviews offer, pricing, order, stock and Paymob changes against the rules in this file. The project grants no MCP permissions in `.claude/settings.json`; Linear access is given in each person's own MCP settings.

## Default branch

- GitHub's default branch stays `develop` (set Nov 7, 2026), so new PRs target it and the workflows GitHub runs only from the default branch (`issue_comment` for `@claude`, `check_run` / `workflow_run` for auto-merge) use `develop`'s copy. App Hosting does not follow it: the dev backend serves `develop`, the prod backend serves `main`.

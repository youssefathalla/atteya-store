**How to edit this file:** one fact per line, as a list item under the heading it belongs to. Add a new rule as its own line, or a new `##` heading for a new topic. ## Admin and staff roles

- **Admin access**: Firebase Auth custom claim `role: 'admin'` (or `role: 'staff'`, below) is the source of truth. Anything else, or a missing claim, is a normal user. Do not grant admin or staff through Firestore data or a client write. `roles/{uid}` is a mirror index written only by the Admin SDK (`functions/scripts/set-admin.mjs`, `listAdmins`, `setUserRole`). It may be missing for an admin granted outside the repo; `--list` still scans Auth claims, while `listAdmins` prefers the `roles` mirror index and verifies each uid with Auth `getUsers` (full `listUsers` only when mirrors are empty or all stale, then heals mirrors). Removing an admin revokes that account's refresh tokens and writes `roles/{uid}.revokeTimeMs` (Auth `tokensValidAfterTime` in milliseconds). Rules reject an admin token whose `auth_time` is older than that value, and admin callables do the same check against Auth. A missing mirror, or a mirror without `revokeTimeMs`, does not block an admin. `auditLogs/{id}` is append-only from the Admin SDK. Clients, including admins, cannot write either collection. While a person is signed in, the app listens to their `roles/{uid}` doc and refreshes the ID token when that mirror role changes.
- **Staff role (<KEY>-194)**: `role: 'staff'` uses the whole dashboard like an admin, except Delete Order and Settings → Team (`listAdmins`, `setUserRole`, `roles` of other people, `auditLogs`), which stay admin only.
- Callables: `requireRole(req, 'staff')` lets staff and admins in, `requireRole(req, 'admin')` admins only (`functions/src/auth/require-role.ts`, `roleFromClaim()` / `canManageStore()`); every store callable uses `'staff'`, `listAdmins`, `setUserRole` and `deleteOrder` use `'admin'`; both check `tokensValidAfterTime`.
- Rules: `canManageStore()` (claim `admin` or `staff` and a current session) guards everything the dashboard reads and writes in `firestore.rules` and `storage.rules`; `isAdmin()` is left only for reading another person's `roles/{uid}` and `auditLogs`.
- Website: `AuthService.canManageStore()` (admin or staff) opens `/admin` (`adminGuard`, the admin layout watcher, the Admin Dashboard links); `AuthService.isAdmin()` is admin only (Team in the sidebar, `adminOnlyGuard` on `/admin/settings/admins`, Delete Order). `/admin/settings` opens Shipping.
- Settings → Team (`/admin/settings/admins`, admins only) adds a person by email as Admin or Staff, lists everyone with Role, Since and Given by, and offers Make Admin / Make Staff / Remove Access per person (the only admin has none); Recent changes lists role changes plus deleted orders and products from `auditLogs`.
- `setUserRole` takes `admin`, `staff` or `user`; it refuses taking the last admin down to staff or no access (`isLastAdminRemoval()` in `functions/src/roles/team-roles.ts`), and any change to less access (admin → staff, anything → user) revokes that person's refresh tokens and writes `revokeTimeMs` (`endsSession()`), so they sign in again with the new role. `functions/scripts/set-admin.mjs --role staff` does the same from a terminal.
- `listAdmins` (name kept so the function is never removed and recreated) returns admins and staff with `role` (admins first), from the `roles` mirror where `role in ['admin','staff']`, falling back to a full Auth scan when no mirrored admin verifies.
- `deleteMyAccount` refuses admin and staff accounts.

## Sign-in and create account

- **Sign-in / create account**: `/login` (client-rendered) offers Google and email/password. `?intent=create` is Create account mode. Both modes show the same always-enabled "Continue with Google" first, then the email form. Only the email part differs: Create account adds the required Terms + Privacy checkbox (links to placeholder `/terms` and `/privacy` until client legal copy lands) and an optional marketing opt-in (unchecked by default) right above Create Account, then `createUserWithEmailAndPassword`. Create Account is not disabled for the box; pressing it without the tick shows the reason under the checkbox. On the "Almost done" step, Continue stays disabled until the terms box is ticked (the only action there). Switching modes keeps the typed values but clears field errors and messages (same component, `#resetOnModeSwitch`). Any signed-in account with no accepted terms in `users/{uid}` (a brand-new Google user from either mode, unless they ticked the box on Create account first) sets `needsConsent`; `/login` shows the "Almost done" step and holds `leaveAfterSignIn` until they accept. In the browser, `AuthService` (`#holdUntilConsent`) sends that account back to `/login?returnUrl=…` from any other page (`/login`, `/terms` and `/privacy` are exempt; skipped when the `users/{uid}` read itself failed, so being offline does not block browsing), and the step offers "Not your account? Sign Out". `favoritesAuthGuard` and `accountAuthGuard` (`requireAgreedAccount`, after `AuthService.waitForAccountReady()`) send that person (and a visitor) back to `/login?returnUrl=…`, `checkoutAuthGuard` (`requireConsentIfSignedIn`, on `/checkout`) sends only that person there and lets visitors check out as guests, `orderPageAuthGuard` (the order page) does the same when the link or this device has the order's view key and otherwise needs the account like `accountAuthGuard` (so a signed-out owner opening a keyless order email goes to sign in), and `createCodOrder` / `createInstapayOrder` / `createPaymobOrder` refuse with `failed-precondition` (`requireAcceptedTerms`: `users/{uid}` needs a `termsVersion` and `termsAcceptedAt`; the exact version is checked only on the website). Signup consent is written to `users/{uid}` (`termsAcceptedAt`, `termsVersion`, `marketingOptIn`, `marketingOptInAt`; owner create-once in rules — deploy `fb:rules:dev` before live writes work). After that the owner may only update `name`, `phone`, `address`, `marketingOptIn` / `marketingOptInAt` (stamped together) and `updatedAt` (always `request.time`); the terms fields never change and delete stays denied. Browser auth is `initializeAuth` with indexedDB then local persistence and no `popupRedirectResolver`, so `__/auth/iframe.js` and gapi are not loaded on ordinary pages. `signInWithPopup`, `signInWithRedirect`, and `getRedirectResult` pass `browserPopupRedirectResolver` explicitly. `getRedirectResult` runs only when `sessionStorage` key `atteya-auth-redirect` was set immediately before `signInWithRedirect`, or when the path is `/login`. The server still uses `getAuth()`. `AuthService` uses `onIdTokenChanged` plus `getIdTokenResult`. On the server the visitor is signed out (`user` null, `role` `'anon'`). `user` is published only after the role is known. Three roles: a visitor is signed out and can browse; a normal user is signed in without the admin claim, can browse and sign out, and cannot open `/admin/*`; an admin has `role: 'admin'` and a current session and can use `/admin/*`. `adminGuard` (also `canActivateChild`) sends a visitor to `/login?returnUrl=…` and a signed-in non-admin home with "This account can't manage the store." The first entry force-refreshes the ID token. The admin layout leaves the page if that person is demoted or signed out. `/playground` (the design-system sandbox) uses the same `adminGuard`, renders on the client (`RenderMode.Client`), and its mobile-menu link shows only when `isAdmin()`. The navbar and mobile-bar account icon (`app-account-menu`) waits until auth is ready in the browser, then shows the sign-in icon (`login`, with a Sign In menu) to a visitor, or the person icon (`person_outline`) that opens the account panel (below) for a signed-in person, with Admin Dashboard in it only when `isAdmin()`. The server renders that same waiting button (a disabled button with an invisible icon, so neither icon flashes before the real one appears) so the prerendered page matches the first client render. Guest favorite hearts open `FavoritesGateService` (explicit Sign in / Create account dialog; never local saves); after auth the tapped product is `add()`ed and the shopper returns via `returnUrl`.

## Saving guest orders to an account

- `claimOrder({ orderId, viewKey })` (`europe-west3`, signed-in callers only, App Check via `requireRole`) links a guest order to the caller: it sets `customerId` and `claimedAt` while the order has no owner, the key matches and the caller's account email is verified (ID token `email_verified`, exposed as `emailVerified` by `requireRole`) and equals the order's `customerEmail` (trimmed, any case; the key alone is not enough, so a forwarded link can't move the order), is a no-op for the same uid, refuses an order owned by another account with `failed-precondition`, and refuses an unverified or different email with `permission-denied` ("Sign in with the verified email you used for this order to save it to your account.").
- `claimOrder` also calls `requireAcceptedTerms` right after `requireRole` (an account that hasn't agreed to the terms gets the same `failed-precondition` as Place Order) and claims only a guest order (`isGuestOrder()` in `guest-order-claim.ts`: the order has the `guest` terms block); any other order answers `not-found` with the same "We couldn't find that order." message as a wrong key (<KEY>-228).
- `app-guest-account-card` waits for `AuthService.waitForAccountReady()` before calling `claimOrder`, and after a Google redirect it saves the order only once `needsConsent()` is false (a new Google account's terms are written a moment after it signs in), so that wait never refuses the save.
- `claimGuestOrdersByEmail()` (`europe-west3`, signed-in callers only, App Check via `requireRole`, then `requireAcceptedTerms`; `functions/src/orders/claim-guest-orders.fn.ts`) links every guest order (it has the `guest` terms block) with `customerId == null` and `customerEmail ==` the caller's lower-cased email to the caller (`customerId`, `claimedAt`, `updatedAt`), at most 50 per call, in one transaction, and returns `{ linked }`; it needs ID token `email_verified == true` (Google counts) and links nothing for an unconfirmed email; an order that already has an owner is never moved. Pure rules in `guest-order-claim.ts` (tested in `guest-order-claim.test.ts`); query index `orders` (`customerId`, `customerEmail`).
- The website calls it from `AuthService` (`#claimGuestOrdersOnSignIn`, browser only, through `CheckoutOrderService.claimGuestOrdersByEmail()`) once per account per tab session (`sessionStorage` `atteya-guest-orders-claimed:<uid>`, cleared on sign-out), as soon as the account has agreed to the terms and its email is confirmed (also right after `refreshEmailVerified()` confirms it); when it linked any, a snackbar says "We added 2 earlier orders to your account." ("1 earlier order" for one), except on the order page, whose Save to My Account card speaks for itself; a failure is silent and is tried again on the next account change or page load.

## Delete account

- **Delete account**: `deleteMyAccount` (`europe-west3`, signed-in callers only, App Check via `requireRole`; `functions/src/auth/delete-account.fn.ts`, pure rule in `account-deletion.ts`) deletes `favorites/{uid}` (with its items), `carts/{uid}`, `users/{uid}`, `roles/{uid}`, the footer `emailSignups` doc for the caller's email, then the Auth user, in that order, so a retry after a failure still works.
- `deleteMyAccount` refuses an admin account (`failed-precondition`) and a sign-in older than 10 minutes (`signedInRecently()`, ID token `auth_time`; the person is asked to sign out and in again). Past `orders` are never touched: they stay for delivery, returns and accounting, and the Terms and Privacy pages say so.
- The website calls it through `AuthService.deleteAccount()` from `app-delete-account-section` (last section of `/account`, after a confirm dialog), then signs out on the device and returns home. Needs `fb:fn:dev` before it works.

## Terms and signed-in pricing

- **Terms and Privacy pages** (`src/app/features/legal/`): written from how the store works (payments, delivery 1 to 4 days in Egypt, guest orders, deletion); contact details come from `STORE_INFO.contact` (email, phone = the InstaPay number, WhatsApp). `CURRENT_TERMS_VERSION` is unchanged; bump both copies only when everyone should accept the terms again.
- Signed-in pricing needs a confirmed email: the order callables price an account whose email is not confirmed like a guest (`offerPricingSignedIn()`), and the website uses `AuthService.offerSignedIn()` (signed in and `email_verified`) for every storefront pricing `signedIn` flag; details in the `offers` skill.

## Confirm your email

- **Confirm your email (<KEY>-174)**: `sendVerificationEmail` (`europe-west3`, signed-in callers only, App Check via `requireRole`; `functions/src/auth/send-verification-email.fn.ts`) sends our own "Confirm Your Email" message through Resend (`RESEND_FROM`, `RESEND_REPLY_TO`, secret `RESEND_API_KEY`), never Firebase's built-in email; the link comes from Admin SDK `generateEmailVerificationLink` and returns to `STOREFRONT_URL` + `/account`, or + `returnPath` when that is a plain path on our site (`verificationContinueUrl()` in `functions/src/auth/verification-send.ts`, tested in `verification-send.test.ts`).
- It refuses an account that is already confirmed or has no email (`failed-precondition`, read from the Auth record, not the token) and allows 3 sends per account per UTC day (`emailVerificationSends/{uid}_{day}`, `expireAt` 2 days later for a TTL policy; over → `resource-exhausted` "You've asked for 3 emails today. Please check your inbox or try again tomorrow.") and 300 for the whole store (`__all_{day}`, same collection; reaching it logs an error, because sign-up takes any address); a send that fails before Resend is called gives both counts back, and every send uses a new Resend idempotency key. Rules deny every client read and write on `emailVerificationSends`, admins included.
- When Firebase Auth itself refuses another link for that address for a while (`TOO_MANY_ATTEMPTS_TRY_LATER` from `generateEmailVerificationLink`, `isTooManyLinkAttempts()` in `verification-send.ts`), the callable gives both counts back and answers `resource-exhausted` "Please wait a few minutes before asking for another email." instead of the generic send-failed `unavailable`.
- The message is `renderVerificationEmail()` (`functions/src/email/verification-email-template.ts`, the same "Bold Black" blocks as the shopper order emails): black header (kicker `ONE LAST STEP`, status `CONFIRM YOUR EMAIL`, one sentence), a full-width **Confirm Email**, three short points (Save orders / Member prices / Favorites, each under a 3px black line), the line that the link expires and can be ignored, and a black footer with "Questions? Message us on WhatsApp" (only when `STORE_INFO.contact.whatsapp` is set) and the site name from `STOREFRONT_URL`.
- The website calls it through `AuthService.sendVerificationEmail(returnPath?)`: automatically and silently by `AuthService` (`#sendConfirmationOnSignIn`) once per account per tab session whenever `emailNeedsConfirming()` and the terms are accepted (Create Account and every later Sign In; `sessionStorage` `atteya-confirm-email-sent:<uid>` is written on success and cleared on sign-out; not while on the order page, whose Save card sends its own), and from the guest order card's Confirm Your Email state (returning to the order page with its key).
- Each successful send logs `Confirm-your-email handed to Resend` with the Resend email id, so a missing email is traced in the Resend dashboard (Emails → Logs).
- `AuthService.emailNeedsConfirming()` (signed in, a `password` provider, token `email_verified` false; Google sign-ins never) shows `app-confirm-email-prompt` (`@shared/ui/confirm-email-prompt`) at the top of the account panel and `/account`: "Confirm your email" with **Resend Email** (spinner only while sending, then "We sent a new link to <email>." or the callable's message through `callableMessage()`).
- While `emailNeedsConfirming()`, `AuthService` runs `refreshEmailVerified()` (`user.reload()`, then a forced token refresh once confirmed) when the app opens and whenever the tab regains focus, so the prompt goes away and the token carries `email_verified`. An unconfirmed account can still browse, add to bag and order.
- Offer and new-arrival emails go only to accounts whose email is confirmed (Google, or a confirmed email/password account); `marketingOptIn` alone is not enough. Nothing sends marketing yet, so this is the rule for whatever sends later.

## Who can read and write what

- **Storefront access**: `firebase/firestore.rules` allows anyone to read documents directly in `settings` (`settings/home`, `settings/navigation`, and any later sibling). Only an admin can write them. Subcollections under `settings` are denied. `roles/{uid}` is readable by that person or an admin, and `auditLogs` by an admin. `carts/{uid}` (the signed-in shopper's bag) is readable and writable only by that person; admins have no access. `emailSignups` and `emailSignupRateLimits` are Admin SDK only (no client access, admins included). Clients cannot write either. `products/{id}` is readable when `published == true`, or by an admin whose session is still current (`isAdmin()`, including `revokeTimeMs`). A public product query must include `where('published', '==', true)` or the rules reject it. Clients, including admins, cannot write product docs: every product write goes through the Admin SDK (`createProduct`, `updateProduct`, `setProductStock`, `confirmCodOrder`, `paymobWebhook`, migrations), so `stock`/`stockBySize`/`inStock` always come from `stockFields()`. `settings/catalog` is a public settings document of published counts (`categories`, `types`, `brands`, `total`). While it is missing or incomplete, the storefront shows every navigation link. The one-time EasyOrders import has been removed. The catalogue was copied once, and products are now added and edited only in the admin (existing docs keep their `eo-…` ids and `source` record as history). Prices are whole Egyptian pounds. Format them with the `egpPrice` pipe. `penceToPounds` stays the legacy GBP pence pipe. Other collections are admin-only. `firebase/storage.rules` lets anyone get one object under `hero/`, `categories/`, `products/`, and `brands/`. Listing those folders is admin-only. Only an admin can upload a JPEG, PNG, WebP, or AVIF under 10 MB there, and `hero/default-hero.jpg` cannot be deleted. Every other path is denied. Storefront pages still load images through ImageKit and the public bucket URL. `importImageFromUrl`, `listAdmins`, `setUserRole`, `setProductStock`, `createProduct`, and `updateProduct` (`europe-west3`) require an admin caller. Image import accepts https on port 443 only, follows at most 3 redirects (each checked again), stops after 10 seconds, caps the body at 10 MB while streaming, and accepts only JPEG, PNG, WebP, or AVIF whose magic bytes match. `firebase.json` runs `npm --prefix functions run build` before a functions deploy. App Check is wired with `APP_CHECK_ENFORCED` defaulting to false. The reCAPTCHA Enterprise site keys are already in `environment*.ts`; turn enforcement on per project only after the Firebase console shows App Check verified traffic close to 100%. There is no rules test suite in this repo.
- **Functions-only collections (<KEY>-233)**: `offerState` has no client read or write (admins included); `searchSyncErrors` is readable by an admin (the Products page counts it) and written only by Cloud Functions. Both have their own `match` and are left out of the admin catch-all in `firestore.rules`.

## Delete Product

- **Delete Product (<KEY>-194)**: `deleteProduct({ productId })` (`europe-west3`, admin or staff; `functions/src/products/delete-product.fn.ts`) deletes one product doc (one colour) and writes `auditLogs` (`action: 'product.delete'`); the search, colour-siblings and counts triggers follow, photos stay in Storage, and bags, favourites, offers and orders keep the id. It refuses (`failed-precondition`) while a Waiting for Payment Cash on Delivery, InstaPay or Bank Transfer order that hasn't taken stock still has that product in `pricing.lines`, because confirming that order needs the product. That check runs before its transaction (Waiting for Payment orders, 500 per page by document id, only the fields it needs), so it never locks open orders. The product editor shows **Delete This Colour** (or **Delete Product** for a one-colour product) on a saved colour, asks first, then opens another saved colour or goes back to Products.

## Product page

- `/product/:slug` is server-rendered through a blocking resolver (`productPageResolver`) plus `TransferState`. A missing product gives a 404 via `RESPONSE_INIT` plus `noindex` and shows Page Not Found (`<app-error-page>`, <KEY>-268); an out-of-stock product is 200 + `noindex` with everything disabled. The resolver also reads active public offers on the server (`PublicOffersReader`, no listener) and transfers them as `TransferOffer` (epoch-ms dates) with `renderedAtMs`; after hydration the PDP prices from the live `OffersService`. The gallery's first photo is `priority`, so on the server `NgOptimizedImage` adds its own `<link rel="preload" as="image">` with the same `imagesrcset` and `imagesizes` (`PDP_GALLERY_SIZES` in `image-kit.loader.ts`); the page adds no preload of its own. On the client, after that TransferState hand-off, the resolver reads the product through `ProductCacheService` (memory only, 60 seconds, 50 slugs, failures dropped). The server always calls `ProductService.getBySlug` and never fills the cache. `appPrefetchProduct` warms one slug after a 100 ms mouse rest or a mouse press, after a 100 ms keyboard rest, or after a still touch. Wheel and pointer-move listeners are passive. A wheel-scroll resets the rest and a moving touch is ignored, so scrolling or tabbing a grid does not read every card. Colour siblings `seed()` the docs `listModelGroup` already loaded. After hydration the product page listens to its own doc (`watchProductDoc` in `features/product/utils/product-live.ts`), so base price and stock replace any cached or prefetched values within about a second and stay live. Unpublished or deleted shows 'No longer available' and disables the options. `clear()` after admin saves is only a same-tab nicety. `product/**`, `category/**`, `brand/**`, and `search` send `Cache-Control: private, no-store` (geo-priced HTML must not sit on App Hosting CDN). A missing product (404) and read errors (503) also use `private, no-store`. Category and brand pages do not set an error status for a failed product read; a deleted or unknown category or brand answers 404 and an empty or hidden one 302 (`catalogPageResolver`, <KEY>-268). `/` uses `private, no-store` as well.

## Catalogue tree and stock

- **Catalogue tree**: `categories/{id}` (two levels, `ancestorIds`, `path`) and `brands/{id}` are public-read when `published == true` (queries must include `where('published', '==', true)`). Products carry `categoryId`, `categoryIds` (leaf plus ancestors), `brandId`, optional `gender` (`women` | `men` | `unisex`; missing = not set, not lockable, not imported), `colors` (closed `ColorId` palette), `tags`, and derived `inStock`. `lockedFields` also accepts `colors` and `tags` (`inStock` is not lockable). `colors` is a list of palette ids (a product can have several, `multi` for 3+ colours); Check catalogue structure → Apply only fills `colors` when a product has none (from colour options, then the name); it never replaces or clears colours that are already set, locked or not. **Look-alike products** (same name and same colour, e.g. the two Head Padel Shorts, both black): add the accent colour in `functions/scripts/data/product-colour-fixes.json` (slug → `{ id, colors }`, palette ids only; the `id` is the document id and is matched first, so it still works after the slug script renames slugs), then run `functions/scripts/fix-product-colours.mjs` (<KEY>-119; dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety). It sets `colors` to exactly that list, locks `colors`, writes `updatedAt` / `updatedBy` (checked against `updateTime`), rejects ids outside the palette and lists products it can't find; run it before `clean-product-slugs.mjs` and Rebuild search after. `functions/scripts/set-product-colors.mjs` (dry run by default, `--apply` to write) fills empty `colors` for the 37 products the backfill could not resolve and locks the field. `functions/scripts/set-product-genders.mjs` (one-off, <KEY>-106; dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety) saves the gender Youssef approved for the 67 clothing products from `functions/scripts/data/product-genders.json` (slug → `women` | `men` | `unisex`): it finds each product by `slug`, writes only `gender`, `updatedAt` and `updatedBy`, prints current and new gender per product ("unchanged" when equal) plus any slug it can't find, never touches products outside the list and never clears a gender; run Rebuild search after applying so Shop's Gender filter sees it. `functions/scripts/merge-size-labels.mjs` (dry run by default, `--apply` to write; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety) gives each size one name (`T2` → `T2 (M)`, `T3` → `T3 (L–XL)`; the bracket version wins) by changing only the size option's value **label**, never its id, so `stockBySize` and variants still match. The dry run lists every distinct size name with its product count and any offer whose size condition uses an old name; run Rebuild search after applying. `functions/scripts/apply-product-copy.mjs` (one-off copy cleanup, Nov 2026; dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety) writes the approved names, short and long descriptions and option labels from `functions/scripts/data/product-copy.json` (slugs, option keys and value ids never change); house style in the **`copywriting`** skill; run Rebuild search, then Check catalogue structure (Preview → Apply) after applying. Algolia mirrors `gender` as a faceted attribute (not `filterOnly`) so Shop can show the Gender filter with counts when data exists (rebuild search after deploy to refresh index settings). Seeds and helpers live in `catalog-taxonomy.ts` (functions and Angular copies, keep identical). `migrateCatalogStructure` (admin callable, passes `add` and `dropLegacy`) seeds categories, brands and `settings/shipping`, and backfills products; `onProductCountsChange` keeps counts current.
- **Product stock**: `stock`, `stockBySize`, and `inStock` are always written together by `stockFields()` / `bootstrapStock()` in `functions/src/products/stock.ts`. `stock` is a whole number ≥ 0 and the source of truth; `inStock` is always `stock > 0`. `stockBySize` is only on products with a `size` option, keyed by that option's value ids, and `stock` equals the sum of the map (Firestore rules cannot sum a map, so `validStock` only checks the integer, `inStock`, and a map of at most 20 entries). Bootstrap runs only when `stock` is not yet a number and never overwrites an existing `stock`: untracked products (`trackStock === false`) get `untrackedDefaultStock()` on every size, or that default as flat `stock` when there is no size option (`currentProjectId()` in `functions/src/project-id.ts` reads `GCLOUD_PROJECT`, then `projectID.value()` from `FIREBASE_CONFIG`, because 2nd-gen functions often leave `GCLOUD_PROJECT` unset; 10 on every project, prod included (`UNTRACKED_DEFAULT_STOCK`, decided Nov 11, 2026; staff correct counts in the admin); an empty id throws instead of writing stock); tracked products with variants sum `variants[].stock` per size id (sizes with no rows are 0), or sum every variant when there is no size option; tracked products with no variants have nothing to count from, so the migration leaves them without `stock` and reports them as `stockMissing` (the admin sets those counts by hand). `trackStock` and `variants[].stock` are no longer read for availability anywhere; only `bootstrapStock()` reads them, once, for a product that has no `stock` yet. Search, the product page, and checkout use `stock > 0` (and `stockBySize` per size) when `stock` is a number, otherwise the stored `inStock` flag (search and checkout treat a missing flag as out of stock). Search does not index `stock` or `stockBySize`. `ProductSchema` has no `trackStock` field and leaves `stock` and `stockBySize` optional with no default, so a product without a count falls back to `inStock`; a missing `inStock` still defaults to `true` in the browser. Do not recompute `inStock` in a trigger that writes the product doc. Admin stock edits go through the `setProductStock` callable (a transaction on the live doc that merges the changed sizes, recomputes `stock`/`inStock` with `stockFields()`, and writes `updatedBy` (uid) and `updatedAt`). There is no client write of stock fields and no stock log yet. The old product form callables (`createProduct` / `updateProduct`, no longer called by the website) write stock only on create and when the sizes change: kept sizes keep their counts, new sizes take the starting count, removed sizes are dropped, all through `stockFields()`. A size sent without an id counts as new even when that id matches an existing size, so its starting count is saved. Adding sizes to a product that had none replaces that total with the per-size starting counts.

## Product form and editor

- **Product form**: `/admin/products/new` and `/admin/products/:productId` (`product-editor.page.ts`) save through the `saveProductModel` admin callable (see the next lines; `createProduct` / `updateProduct` stay deployed but the website no longer calls them). There is no client product write any more. Dashboard products use a browser-generated Firestore auto-id, `source: null`, `variants: []`, every lockable field locked, and `createdBy`/`updatedBy`. The slug is set once on create (unique, from the name when blank) and never changes, except once, before launch, by `functions/scripts/clean-product-slugs.mjs` (<KEY>-115; dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety; run it last, after the other one-off scripts that find products by their old slug): every product gets its name (accents folded, `a-z 0-9` joined by `-`), and each `colors` id the name doesn't already say (`multi` adds nothing) is added only when another product has the same name slug, i.e. the same product in another colour (<KEY>-118): `nox-socks-white` / `nox-socks-black`, but a one-colour product is just `babolat-thermal-bottle`; a slug already taken by an earlier product (document-id order) gets `-2`, `-3` and is listed as a clash to rename. It writes only `slug`, `updatedAt` and `updatedBy` (checked against `updateTime`), never document ids, lists links in `settings/*` that point at an old address (fixed by hand), and old addresses are not redirected; run Rebuild search after applying. The product form keeps never changing the slug. Anything that stores a product reference keeps the id (bag lines, favourites, orders, offers) and reads the live slug. The description is plain text turned into `<p>` HTML on the server, and it's written only when it changed. Product text has three jobs: `summary` (Short summary, ≤ 7 words: cards, the bag, search), `descriptionHtml` (Description, one or two sentences of prose, shown on the product page under the price) and `details` (Details box, one fact per line, at most 20 lines of 200 characters; trimmed, a leading "•" removed, blanks dropped by `detailLine()` on both sides). `details` is always sent and saved (`[]` = none; a request without the key leaves the saved list alone) and is not searched. The product page lists it in its own section under the photos, before Shipping, titled by `productDetailsTitle()` from the category setting (`categoryPageFor()`, below; today **Materials** under `apparel` or `supports`, **Specifications** for everything else); hidden when empty. `functions/scripts/split-product-details.mjs` (one-off, Nov 2026; dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety) split the long descriptions once: the text before the first "• " line stays the description, each "• " line becomes a `details` line; products with `details` already, no "• " line, other HTML, or text after the bullets are listed and left alone. Only the `size` option is editable, and other options are kept. Photos uploaded in a session and not kept are deleted. Photos removed from a saved product stay in Storage. Stock fields in the product form are text inputs checked by `isAllowedCount()`, with inline errors. The callables also reject bad counts; `stockFields()` clamping is only a safety net. The description is turned into textarea text block by block (`plainFromHtml`), which round-trips with `descriptionToHtml`. A photo link to one of our own files outside the target folder is copied by `importImageFromUrl` (`path` input) into that folder. Width/height are the natural size, and the alt is the product name. Nothing deletes saved photos yet; any future cleanup must check every reference first, because older products and hero slides may share files.
- **One page per product and its colours (<KEY>-205)**: the product editor opens every product with the same `modelGroup` as the opened id as one colour tab each (no `modelGroup` = one colour); there is no "Model group" field any more.
- **Product editor layout (<KEY>-271, <KEY>-275)**: `.product-editor-grid` (`src/styles/tailwind/components/product-editor.css`) keeps one page order (Product, then Sizes / Tags and badges / Offers / What shoppers see, then Price and Organise, then Colours) and places it by the admin `<main>` container width without gaps under short cards: one column on phone; from 40rem two newspaper columns (CSS `columns`, the small-card and side wrappers `display: contents`, each card `break-inside: avoid`) with Colours across both; from 64rem three columns (`2fr | 1fr | 1fr`, middle at least 18rem, right at least 20rem), Product then Colours on the left, the four small cards in the middle, Price and Organise on the right.
- The product editor's prices are **Selling price (EGP)** (`price`) and **Price before discount (EGP)** (`compareAtPrice`, only when on sale, shown crossed out), with a "Shoppers see" line under them; Badge and Style are Material selects.
- The product editor's Category picker is one tree (`buildLeafCategoryOptions()`: each main category once, bold and pickable, the ones inside it pushed in under it, in Categories & Brands order, hidden ones marked); the closed box shows "Apparel › Shorts" (`app-select-input` `levelKey` / `triggerKey`).
- Shared by every colour, written to every colour doc on save: name, short summary (7-word counter), description, details, type, category, brand, gender, players, weight, tags, marketing badge, new arrival, the size list, and the price unless a colour has its own.
- Per colour (one product doc each): its colours (`colors`, the first is the tab's colour; an accent colour stays as saved), photos (`products/<that colour's doc id>`), stock per size, sizes it isn't made in (left out of that doc's size option; **Not Made** / **Make It**), its own price and old price ("Different price for …"), and `published` (**Hide This Colour** / **Show This Colour**).
- **Add Colour** offers the palette minus the colours already there (at most 12); a new colour gets a browser-made doc id, the shared details, empty photos and 0 stock, and is shown once it has a photo (save refuses a shown colour with no photo).
- `getProductModel({ productId })` (`europe-west3`, admin) returns the model's colour ids, each with a `version` (`contentVersion()`: a sha256 of the doc's fields, leaving out `colorSiblings`, which the colour-siblings trigger rewrites after every save); the page reads versions first, then the docs, so a change in between makes the save refuse rather than overwrite.
- `saveProductModel({ anchorId, shared, colours })` (`europe-west3`, admin; `functions/src/products/product-model.fn.ts`, pure rules in `product-model.ts`, tested in `product-model.test.ts`) writes every colour in one transaction: each saved colour must still have its `version` and the model must have no other member, else `aborted` "Someone changed this product while you were editing. Reload to see it."; stock goes through `stockFields()`; `updatedAt` / `updatedBy` on every colour; new docs lock every lockable field, saved ones lock what changed.
- Every `saveProductModel` save writes each colour's full stock (`stock`, `stockBySize`, `inStock` through `stockFields()`) from the boxes on the page; an order that took stock after the page loaded changes the version, so that save is refused instead of putting the stock back.
- Size ids are shared: a saved size keeps its id, a new size gets its kebab label (deduped), and a colour that already had a size of that name under another id keeps that id, so `stockBySize`, bag lines and offer size rules keep matching.
- When a product gets its second colour, the server gives every colour one `modelGroup` from the name (same rule as `link-colour-models.mjs`, `-2` when taken); colours already in a model keep it.
- A new colour's slug is the name plus the colour (`bullpadel-padel-shorts-green`) when the product has more than one colour, otherwise the name, unique as before; saved slugs never change.
- An untouched description is not sent, so each saved colour keeps its own (old-store formatting stays) and a new colour copies the first saved colour's; it is always sent when the colours had different descriptions.
- The page shows "Some colours had different details. Saving uses what you see here." when the saved colours differ in name, summary, description, details, category, brand, gender, players, weight, sizes, type, tags, marketing badge or new arrival, and lists the running offers that cover the product (every colour, or which colours) with **Open Offers**, plus "What shoppers see" per colour (Shown · EGP 599, Hidden (sold out), Hidden).

## Size & Fit, old store, colour cards and players

- **Size & Fit (product page, <KEY>-203)**: `sizeGuidesFor()` (`features/product/utils/size-guide.ts`) builds one table for `app-size-guide`: a product with a `size` option whose category uses the clothing size chart (`categoryPageFor()`, below; today `apparel` and its sub-categories except `socks`). The Weight (kg) row comes first (t-shirts S–3XL, hoodies S–L), then the body rows, then Shirt Width and Shirt Length on t-shirts; columns are the sizes that have a value (XS–3XL, `2XL` like the size buttons) and an empty cell shows a dash. Values are fixed in that file as the client gave them (shirt inches are cm ÷ 2.54; weight stays in kg when Inches is picked). Centimetres / Inches and Men / Women use `mat-button-toggle-group.pill-switch`. The table box uses `appHorizontalScroll` (mouse drag only while it overflows, wheel off, no snapping; touch and trackpads scroll natively, <KEY>-210).

## Size chart and details title per category

- **Size chart and details title per category (<KEY>-250)**: category docs may hold `sizeChart` (`'clothing'` | `'none'`) and `detailsTitle` (`'materials'` | `'specifications'`); `null` = same as the parent (saved by staff), a missing field = the built-in default `BUILT_IN_CATEGORY_PAGE` in `catalog-taxonomy.ts` (both copies: `apparel` clothing + Materials, `socks` no chart, `supports` Materials).
- `categoryPageFor(product, saved)` (`core/services/products/utils/product-details.ts`) takes the leaf category's value, else its parent's; nothing anywhere = no size chart and Specifications. The chart tables (the client's measurements) stay in `size-guide.ts`.
- `productPageResolver` takes those fields for the product's categories from `ShopCategoriesService` (the published categories the main layout already reads once per request and seeds as `shop-categories`; `sizeChart` / `detailsTitle` ride on `ShopCategorySource`, so no extra read) and sends them in `ProductPageResult.categorySettings` through TransferState, so the server HTML and the first render match; a hidden category is not in that list, so its products use the built-in default or the parent's setting, and when that read fails the built-in defaults stand in.
- Categories & Brands' category dialog shows **Size Chart** (Clothing size chart / None / Same as parent) and **Details Title** (Materials / Specifications / Same as parent; "Same as parent" only on sub-categories) and always sends both to `saveCategory` (`null` = same as parent; a request without them leaves the doc alone).
- Check catalogue structure (`migrateCatalogStructure`) writes the built-in values onto the built-in category docs only when the field is missing, never over a saved choice.

## Shop tabs

## Search and one card per model

- **Admin product search** uses Firestore `searchTokens` (not Algolia): `buildSearchTokens()` in `functions/src/products/search-tokens.ts` (Angular copy in `src/app/core/services/products/search-tokens.ts`, keep the shared part identical). Words go through `searchWords()` (NFD accent folding, lowercase English/Latin letters and digits). Tokens are each word plus its 2+ letter prefixes; a one-letter query word matches as a prefix in the client filter. After changing how tokens are built, run Catalogue tools → Check catalogue structure (Preview → Apply) on each project to rebuild them. Tokens are not in Algolia records.
- **One card per model (<KEY>-186)**: every product list shows each model (`modelGroup`) once; the other colours are under its photo. Algolia records carry `distinctKey` (`model:<modelGroup>`, or `product:<id>` without a model, `distinctKeyFor()` in `product-record.ts`) and the index sets `attributeForDistinct: 'distinctKey'`, `distinct: 1` (forwarded to the price replicas), so the best-ranked colour of each model is returned (in stock first; a Colour filter returns the matching colour); `SearchService` sends `distinct: true` and, on Shop, `facetingAfterDistinct: true` so results and filter counts count models. Firestore lists (category and brand pages, home New Arrivals and Padel) go through `onePerModel()` (`@core/services/products`, tested by `npm run test:cart`). Favorites keeps every colour the shopper saved.
- **Colours with the same name are one model**: products with the same name (accents and case ignored) are colours of one product and must share a `modelGroup`. `functions/scripts/link-colour-models.mjs` (<KEY>-186; dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety) gives each such group one model (from the name, or the model one colour already has), refreshes `searchTokens`, locks `modelGroup`, and lists groups with two different models or a clashing model name as CHECK; run Rebuild search after applying.
- **Colours with different names (<KEY>-201)**: colours of one product whose names differ (Babolat and Bullpadel Padel Shorts plus their Printed Padel Shorts) are listed by hand in `functions/scripts/data/colour-model-groups.json` (model → document ids); `link-colour-models.mjs` links those first, moving a listed product out of its old model, and leaves them out of the name groups; a missing id, an id listed twice or the model used by an unlisted product is CHECK.
- **One product per colour (<KEY>-206)**: `functions/scripts/split-colour-products.mjs` (dry run by default, `--apply` to write, prod also needs `--confirm-prod`; on dev the manager agent applies after a dry run, prod only on Youssef's OK: see Deploy safety) splits every product whose `colour` option has 2 or more choices into one product per colour (the first colour keeps the document and slug, the others get new documents with slug name + colour and `source: null`, one `colors` entry, the shared `modelGroup`, every field locked, 5 per size through `stockFields()`), with each colour's photos from `functions/scripts/data/colour-split.json` (slug → colour name → photo paths, filled after the dry run and approved by Youssef; a missing product or colour, a colour the model already has, or a real stock count instead of the placeholder is CHECK and not split; offers naming the original id are listed to update by hand); it also sets 5 per size on every other colour of a model whose stock is still the placeholder (every size at `UNTRACKED_DEFAULT_STOCK`, or flat 10) and lists real counts it keeps; bags and orders are never edited; run Rebuild search after applying.
- **Colour split overrides**: a `colour-split.json` entry may be `{ "photos": { colour → paths }, "dropColours": [names], "replaceRealStock": true }`; a dropped colour choice gets no product (its variant rows go too, the first remaining colour keeps the document), and `replaceRealStock` replaces a real count with the starting 5 (printed as a NOTE) instead of a CHECK.
- **Search (Algolia)**: `syncProductSearch` mirrors published products to the index (records carry `newArrivalUntilMs`, 0 when not a new arrival, `filterOnly`, for Shop's New arrivals filter `?newArrivals=1`; run Rebuild search after a functions deploy that changes record fields). Records' `onSale` (Shop's Sale filter, `?onSale=1`) is true for an old (compare-at) price above the price, or when a live public offer for everyone of type Percent off, Amount off or Set price lowers the card price (`computeProductOfferFields` in `functions/src/search/product-record.ts`, so `onOfferWritten` and `refreshOfferPricing` move a product in and out of Sale with the other offer fields); Buy X Get Y, Free gift, Free shipping and tiered offers never put a product in Sale, and `discountPercent` stays the compare-at percent only (tests: `product-record.test.ts`). `reindexSearch` ("Rebuild search" in Catalogue tools) rewrites settings and records; failures land in `searchSyncErrors/{id}`. Indexes: `dev_products` / `prod_products` plus `_price_asc` / `_price_desc` replicas (sort on `displayPrice`). Dev and prod use separate Algolia applications (prod `EW50BE3MCR` / `attiya-store`). `ALGOLIA_WRITE_KEY` is a Secret Manager secret; never commit an Algolia Admin or Write key. The storefront uses the search-only key from `environment*.ts` through `SearchService` (lazy `algoliasearch/lite`, warmed when the search page is created in the browser). `/search` is server-rendered with `Cache-Control: private, no-store`: the heading, the query, and the first page of hits (when `q` has at least 2 characters) are in the HTML via the results `resource()` and `TransferState`; card prices use Algolia display fields until live offers hydrate. A preconnect to `{appId}-dsn.algolia.net` is added from the search component. The first two result images (one mobile row) use `priority`.

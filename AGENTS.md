# 🤖 AI Agent Master Guide

This repository contains a production-grade **Angular v22+ (Zoneless, Signal-First)** application with **Tailwind CSS v4** and **Angular Material M3**.
Adhere strictly to these core directives to ensure maximum performance, clean architecture, and seamless collaboration.

---

## 🧠 1. Core Architectural Directives

### 🅰️ Angular & Signals (Strict Modern Standards)

- **Signal-First Reactivity**: Use `signal()`, `computed()`, and `effect()`. Zero Zone.js dependencies (`fakeAsync`, `tick` are forbidden).
- **Resource-First Data Fetching (v22+)**: Use `resource()` (Promises) and `rxResource()` (Observables/streams). Manual loading/error states (`isLoading = signal(false)`, manual `try/catch`, `error = signal(...)`) are forbidden.
- **Inputs & Outputs**: Use `input()` / `input.required()` and `output()`. No legacy `@Input` or `@Output`.
- **Control Flow**: Modern template syntax only (`@if`, `@for`, `@let`, `@switch`). No `*ngIf` or `*ngFor`.
- **Template Access**: Templates can read `private` component members; avoid redundant `protected` visibility.
- **Defaults in v22+**: Standalone (`standalone: true`), `OnPush`, and Zoneless are defaults in v22+. Do not write redundant flags or `provideZonelessChangeDetection()`.
- **HTTP Configuration**: `HttpClient` is provided in root by default. `provideHttpClient(...)` is optional and only needed when registering interceptors (`withInterceptors`), XSRF protection, or `withXhr()`. FetchBackend is the default engine (`withFetch()` is deprecated).
- **Services**: Use `@Service()` from `@angular/core` instead of legacy `@Injectable({ providedIn: 'root' })`.
- **Forms**: Prefer Signal Forms for modern state management.
- **Deep Reference**: Activate the **`angular-developer`** skill and review `.agents/skills/angular-developer/references/angular-version-matrix.md`.

### 🧭 Routing & Route Data

`withComponentInputBinding()` is **enabled** in `app.config.ts`, so route state flows into components as signals — no `ActivatedRoute` plumbing.

- **Router Resources (v22.2+)**: Route-level data fetching uses `resources: (ctx) => ({ ... })` with `nonBlocking(...)` instead of legacy resolvers. The resolved or streaming resource binds directly to component `input.required<Resource<T>>()`.
- **Throwing Redirects**: Throw `new RedirectCommand(router.parseUrl(...))` directly inside guards and resource loaders rather than returning UrlTrees.
- **Route data is an `input()`**: path params, matrix params, query params, static `data`, and resource output all bind to matching input names (`readonly id = input.required<string>();`).
- **Precedence on duplicate keys** (lowest to highest): query params -> path/matrix params -> static route `data` -> resource/resolver data.
- **`ActivatedRoute` is the exception**: reach for it only inside guards or when parent/child route state is needed. Never inject it just to read route params.
- **Lazy by default**: prefer `loadComponent` / `loadChildren` for feature routes.

### 🎨 Design System & Styling

- **The Contract**: Token vocabulary and hard bans live in `.cursor/rules/design-system.mdc` (Cursor auto-loads for `.html`, `.css`, `.scss`, and `.ts`), `.agents/rules/design-system.md` (Antigravity glob rule), and `.claude/rules/design-system.md` (Claude Code, scoped to the same files). - **Zero Tailwind on Angular Material**: Angular Material components (`button[matButton]`, `button[matIconButton]`, `<mat-icon>`, `<mat-menu>`, `<mat-drawer>`, etc.) are already fully styled by the M3 theme. **NEVER** apply Tailwind styling, color, transition, or hover classes to Material components. Only style **native HTML elements** (`<div>`, `<nav>`, `<section>`, `<ul>`, `<a>`, etc.) unless explicitly instructed by the user.
- **Monochrome (Black & White) Identity**: Brand aesthetic is strictly Black & White. `primary` is black; default text is naturally `text-on-surface` (inherited from `body`). **NEVER write `text-on-surface` on any element** — it is already the default inherited color and writing it is banned as redundant class bloat. Never add redundant child color overrides (e.g. `<span class="text-primary">.</span>`), and inherit colors cleanly.
- **Layout Alignment Shortcuts**: Always use custom layout shortcuts instead of writing verbose flex classes: Row: `elements-center`, `elements-start`, `elements-end`, `elements-between`. Column: `elements-center-col`, `elements-start-col`, `elements-end-col`, `elements-between-col`.
- **United Border Shape (`border-shape`)**: Single source of truth for corner radius across all elements is `border-shape` (`border-radius: var(--border-shape, 2px)`). Arbitrary `rounded`, `rounded-corner-xs`, `rounded-sm`, `rounded-md`, `rounded-lg` are strictly banned.
- **Button Loading State Standard**: During action loading (`isSaving()`, `isUploading()`, etc.), render **only the spinner** (`<mat-progress-spinner mode="indeterminate" diameter="18" />`). Never display text alongside a spinner. Swap the label/icon cleanly with `@if (isLoading()) { <mat-progress-spinner ... /> } @else { <mat-icon ... /> <span>Label</span> }` and provide `[attr.aria-label]="isLoading() ? 'Action...' : null"` for screen readers.
- **United Button Icon Sizing**: All `<mat-icon>` placed inside buttons (`matButton`, `matIconButton`, or native `<button>`) automatically default to `DEFAULT_BUTTON_ICON_SIZE` (`'lg'`) via `MatIconDirective` and `.mat-mdc-button-base mat-icon`. Never write `size="..."` on any icon inside a button.
- **Universal Plain-Language Microcopy**: All user- and admin-facing copy (buttons, dialogs, snackbars, alerts, hints, empty states) must speak the natural, everyday language of general users. Always communicate user intent and real-world outcomes rather than technical mechanisms, developer jargon, or underlying systems. Keep action labels simple, familiar, and active, and ensure all feedback is constructive, reassuring, and intuitive. Names of payment methods and order statuses are written as names, with capitals on the main words and small connecting words: **InstaPay**, **Card or Wallet**, **Cash on Delivery**, **Waiting for Payment**, **Payment Failed** (also inside sentences, emails and server messages). Buttons, menu items and dialog actions use the same title case: capitals on the main words, small connecting words (a, an, the, and, or, of, on, in, at, to, by, for, with, from) in lower case unless first or last, brand words as written ("Place Order", "Add to Bag", "Send on WhatsApp", "Message Us on WhatsApp", "Sign In", "Back to the Store"). Sentences, hints, snackbars, aria-labels and status badges such as "In stock" / "Not set" stay sentence case. Full house style: the **`copywriting`** skill.

### 📐 Layout & Viewport Sizing Standards

1. **Top-Level Query Container**:
   - `<main>` inside `main.component.html` carries `@container`. Page-level sections and cards must use `cqw` to remain fluid relative to drawer open/close and responsive main layouts.
   - Never place `@container` on the same element where `cqw` padding is declared (CSS cannot query itself).
2. **Angular Component Host Sizing**:
   - All section and page components (`app-*-section`, `app-*`) must define `host: { class: 'block w-full' }` in `@Component()` to prevent `display: inline` height/width collapse.
3. **Full-Viewport Sections**:
 - Full-screen heroes directly below the stacked top chrome must use `h-[calc(100dvh-var(--storefront-top-chrome,56px))]`. `--storefront-top-chrome` is measured from the shipping banner + desktop nav stack (fallback `56px` / `h-14` when chrome is not mounted).
 - When a full-height hero is specified, do NOT add `aspect-*` (`aspect-video`, `aspect-21/9`) to the slide containers, as `aspect-ratio` overrides height in modern CSS.
4. **Section Spacing**:
   - Use `.container-content` as the single unified class for page section layout and responsive container padding (`p-[5cqw]`). Do not append `.section-space` to elements that already have `.container-content`.

### 🛡️ Data Validation (active) & Firebase (target state)

- **Strict Validation — ACTIVE**: `valibot` is installed and in use (`src/app/shared/schemas/`, `src/app/shared/ui/status-badge/status.model.ts`). Pipe all external data through a schema (`v.parse()` / `v.safeParse()`) before use. Use `createValibotConverter()` for Firestore documents. See the **`typescript`** skill for the schema rules.

> [!IMPORTANT]
> **Native Firebase JS SDK (`firebase`) is standard.** Do NOT install or use `@angular/fire`. Native Firebase SDK functions (`getDoc`, `signInWithEmailAndPassword`, `onSnapshot`) are framework-agnostic, take explicit instances, and do NOT require an Angular injection context or `runInContext()` wrappers. Storage and Functions are not registered at startup. `injectStorageAsync()` and `injectFunctionsAsync()` (`@core/firebase`, region `europe-west3`) return a loader. Call them from an injection context, store the function, and invoke it on each use. A successful SDK load is reused. A failed chunk load is dropped so the next call retries.

- **Admin access**: Firebase Auth custom claim `role: 'admin'` is the source of truth. Anything else, or a missing claim, is a normal user. Rules and callables check `token.role == 'admin'` only. Do not grant admin through Firestore data or a client write. `roles/{uid}` is a mirror index written only by the Admin SDK (`functions/scripts/set-admin.mjs`, `listAdmins`, `setUserRole`). It may be missing for an admin granted outside the repo; `--list` still scans Auth claims, while `listAdmins` prefers the `roles` mirror index and verifies each uid with Auth `getUsers` (full `listUsers` only when mirrors are empty or all stale, then heals mirrors). Removing an admin revokes that account's refresh tokens and writes `roles/{uid}.revokeTimeMs` (Auth `tokensValidAfterTime` in milliseconds). Rules reject an admin token whose `auth_time` is older than that value, and admin callables do the same check against Auth. A missing mirror, or a mirror without `revokeTimeMs`, does not block an admin. `auditLogs/{id}` is append-only from the Admin SDK. Clients, including admins, cannot write either collection. While a person is signed in, the app listens to their `roles/{uid}` doc and refreshes the ID token when that mirror role changes.
- **Sign-in / create account**: `/login` (client-rendered) offers Google and email/password. `?intent=create` is Create account mode. Both modes show the same always-enabled "Continue with Google" first, then the email form. Only the email part differs: Create account adds the required Terms + Privacy checkbox (links to placeholder `/terms` and `/privacy` until client legal copy lands) and an optional marketing opt-in (unchecked by default) right above Create Account, then `createUserWithEmailAndPassword`. Create Account is not disabled for the box; pressing it without the tick shows the reason under the checkbox. On the "Almost done" step, Continue stays disabled until the terms box is ticked (the only action there). Switching modes keeps the typed values but clears field errors and messages (same component, `#resetOnModeSwitch`). Any signed-in account with no accepted terms in `users/{uid}` (a brand-new Google user from either mode, unless they ticked the box on Create account first) sets `needsConsent`; `/login` shows the "Almost done" step and holds `leaveAfterSignIn` until they accept. In the browser, `AuthService` (`#holdUntilConsent`) sends that account back to `/login?returnUrl=…` from any other page (`/login`, `/terms` and `/privacy` are exempt; skipped when the `users/{uid}` read itself failed, so being offline does not block browsing), and the step offers "Not your account? Sign Out". `checkoutAuthGuard` and `favoritesAuthGuard` (`requireAgreedAccount`, after `AuthService.waitForAccountReady()`) send that person back to `/login?returnUrl=…`, and `createCodOrder` / `createInstapayOrder` / `createPaymobOrder` refuse with `failed-precondition` (`requireAcceptedTerms`: `users/{uid}` needs a `termsVersion` and `termsAcceptedAt`; the exact version is checked only on the website). Signup consent is written to `users/{uid}` (`termsAcceptedAt`, `termsVersion`, `marketingOptIn`, `marketingOptInAt`; owner create-once in rules — deploy `fb:rules:dev` before live writes work). Browser auth is `initializeAuth` with indexedDB then local persistence and no `popupRedirectResolver`, so `__/auth/iframe.js` and gapi are not loaded on ordinary pages. `signInWithPopup`, `signInWithRedirect`, and `getRedirectResult` pass `browserPopupRedirectResolver` explicitly. `getRedirectResult` runs only when `sessionStorage` key `atteya-auth-redirect` was set immediately before `signInWithRedirect`, or when the path is `/login`. The server still uses `getAuth()`. `AuthService` uses `onIdTokenChanged` plus `getIdTokenResult`. On the server the visitor is signed out (`user` null, `role` `'anon'`). `user` is published only after the role is known. Three roles: a visitor is signed out and can browse; a normal user is signed in without the admin claim, can browse and sign out, and cannot open `/admin/*`; an admin has `role: 'admin'` and a current session and can use `/admin/*`. `adminGuard` (also `canActivateChild`) sends a visitor to `/login?returnUrl=…` and a signed-in non-admin home with "This account can't manage the store." The first entry force-refreshes the ID token. The admin layout leaves the page if that person is demoted or signed out. `/playground` (the design-system sandbox) uses the same `adminGuard`, renders on the client (`RenderMode.Client`), and its mobile-menu link shows only when `isAdmin()`. The navbar account menu waits until auth is ready in the browser, then shows Sign in, or the person's name, Sign out, and Admin dashboard only when `isAdmin()`. The server renders that same waiting button so the prerendered page matches the first client render. Guest favorite hearts open `FavoritesGateService` (explicit Sign in / Create account dialog; never local saves); after auth the tapped product is `add()`ed and the shopper returns via `returnUrl`.
- **Storefront access**: `firebase/firestore.rules` allows anyone to read documents directly in `settings` (`settings/home`, `settings/navigation`, and any later sibling). Only an admin can write them. Subcollections under `settings` are denied. `roles/{uid}` is readable by that person or an admin, and `auditLogs` by an admin. Clients cannot write either. `products/{id}` is readable when `published == true`, or by an admin whose session is still current (`isAdmin()`, including `revokeTimeMs`). A public product query must include `where('published', '==', true)` or the rules reject it. Clients, including admins, cannot write product docs: every product write goes through the Admin SDK (`createProduct`, `updateProduct`, `setProductStock`, `confirmCodOrder`, `paymobWebhook`, migrations), so `stock`/`stockBySize`/`inStock` always come from `stockFields()`. `settings/catalog` is a public settings document of published counts (`categories`, `types`, `brands`, `total`). Other collections are admin-only. `firebase/storage.rules` lets anyone get one object under `hero/`, `categories/`, `products/`, and `brands/`. Listing those folders is admin-only. Storefront pages still load images through ImageKit and the public bucket URL. `importImageFromUrl`, `listAdmins`, `setUserRole`, `setProductStock`, `createProduct`, and `updateProduct` (`europe-west3`) require an admin caller. Image import accepts https on port 443 only, follows at most 3 redirects (each checked again), stops after 10 seconds, caps the body at 10 MB while streaming, and accepts only JPEG, PNG, WebP, or AVIF whose magic bytes match. `firebase.json` runs `npm --prefix functions run build` before a functions deploy. App Check is wired with `APP_CHECK_ENFORCED` defaulting to false. ### 🖼️ Image Delivery & Optimization Architecture (ImageKit + Firebase Storage + Cloud Functions)

- **Proxy Architecture**: Master media files reside permanently in Firebase Cloud Storage. ImageKit acts as an external Web Folder origin (`https://storage.googleapis.com/<bucket>/`), intercepting requests to perform real-time resizing, WebP/AVIF compression, and global CDN delivery. That Google Cloud Storage URL is authorized by bucket IAM, not by `firebase/storage.rules`. Shop-category images are stored under `categories/` and follow the same path (`NgOptimizedImage` → ImageKit, then `buildStorageUrl()` on failure). The public single-object `get` in storage rules (all four image folders: `hero/`, `categories/`, `products/`, `brands/`) only covers Firebase SDK and `firebasestorage.googleapis.com` reads; storefront images do not depend on it. Folder listing stays admin-only. Photos from the one-time EasyOrders copy live under `products/<docId>/<sha1 of the source URL>.<ext>`. DigitalOcean serves some JPEGs as `Content-Type: image/jpg`; `canonicalContentType()` in `functions/src/images/safe-image-fetch.ts` treats that as `image/jpeg` before the type and magic-byte checks.
- **Environment Isolation**:
  - **Dev (`environment.ts`)**: `https://ik.imagekit.io/atteyastore/dev/` fetching from `atteya-store-dev.firebasestorage.app`.
  - **Prod (`environment.prod.ts`)**: `https://ik.imagekit.io/atteyastore/` fetching from `attiya-store.firebasestorage.app`.
  - Dev uploads, previews, and tests never collide with or affect production assets or cache.
- **Angular Image & Fallback Standards**:
  - Provided via `provideImageKitLoader(environment.imageKitUrl)` in `app.config.ts`.
  - **Strictly use `NgOptimizedImage` (`[ngSrc]`) paired with `AppImageFallbackDirective` (`[appImageFallback]`)** for all storefront and preview media. Raw `<img [src]>` for media assets is banned.
  - `[appImageFallback]` automatically renders a monochrome `.skeleton` shimmer while loading and fails over once to `buildStorageUrl()` if ImageKit CDN fails or is still syncing.
  - Never build Storage or ImageKit URLs by hand; always use `normalizeImageKitPath()`, `buildImageKitUrl()`, and `buildStorageUrl()` from `@shared/utils/image`.
- **Media Uploads, Galleries & Validation**:
  - Use `ImageAssetSchema` / `ImageGallerySchema` (`@shared/schemas`) with required SEO alt text (max 125 chars) and raster formats only (JPG, PNG, WebP, AVIF — SVG is banned).
  - Use `<app-image-picker>` (`@shared/ui/image-picker`) for single images and `<app-image-gallery-editor>` (`@shared/ui/image-gallery-editor`) for multi-image galleries (max 8 images, index 0 = Main image, pre-generated ID folder `products/<productId>`).
  - Use `ImageSourceService` (`@core/services/storage`) for validating uploads, probing ImageKit via CORS-safe `new Image()`, and importing external https links via the `importImageFromUrl` Callable Cloud Function (`functions/`). The browser does not fetch that URL itself.
  - Track uncommitted session uploads per draft using `StorageAssetTracker` (`@core/services/storage`).
- **Skeleton Placeholders vs Blocking Spinners**:
  - Use `<app-skeleton>` (`@shared/ui/skeleton`) or `.skeleton` for layout/content placeholders (`@defer` placeholders, `resource.isLoading()` cards/lists/text) to prevent Cumulative Layout Shift (CLS).
  - Reserve `<mat-progress-spinner>` and `<app-loader>` for active button actions or blocking overlays.

> [!IMPORTANT]
> **Develop-only until launch (TEMPORARY rule — delete this block after the final merge to `main`).**
> Until the app is finished and handed over, `develop` is the only working branch. All work is built, pushed and tested on `develop`.
> - Do **not** merge `develop` → `main`, open a `develop` → `main` PR, or ask whether to. Do not list "merge to main" as a next step or a test prerequisite.
> - Dev deploys run from an up-to-date `develop` (`DEPLOY_BRANCH.dev` in `scripts/firebase-guard.mjs`). Prod deploys still require `main`, and there are none until launch.
> - The board's **QA** step is "pushed to `develop` + dev deploy", not a merge to `main`.
> - **Last step of the project** (the "Final merge to main" task on the board): merge `develop` → `main` with a merge commit, set `DEPLOY_BRANCH.dev` back to `'main'`, delete this block, then run the prod rollout. After that the normal flow below applies again: new client features are built on `develop` and merged to `main` when each one is finished.

- `main` (default) and `develop` are long-lived. Working branches (`feature/…`, `fix/…`, `hotfix/…`, `refactor/…`, `perf/…`, `docs/…`, `test/…`, `chore/…`, `ci/…`; see the **`branch-naming`** skill) come off `develop`, and their PRs target `develop`.
- **Worktrees stay inside the project**: parallel agent sessions work in `.claude/worktrees/<name>` (gitignored), never in a folder outside the project. Create one from the main project folder with `git worktree add .claude/worktrees/<short-name> -b <type>/<short-name> origin/develop`, run `npm ci` in it, and remove it with its branch after the PR merges. The main project folder stays on an up-to-date `develop`. `.claude/settings.json` sets `worktree.baseRef: "head"` so Claude Code's own worktrees (`--worktree`, subagent isolation) start from that `develop` instead of `main`, and the branch hook blocks `git worktree add`/`move` to any other path.
- **Squash** feature PRs into `develop`. Use **"Create a merge commit"** (never squash) for `develop` → `main` and for any PR that brings `main` back into `develop`. A squash there drops the shared history, and the next `develop` → `main` PR conflicts even when the files already match.
- GitHub's "Automatically delete head branches" setting is **off** because it would also delete `develop` after a `develop` → `main` PR. `.github/workflows/delete-merged-branches.yml` deletes a merged PR's branch instead and always skips `develop` and `main`. A deleted branch can be restored from its PR page.
- Firebase deploys run only from an up-to-date `main` (see **Deploy safety**), so a change reaches dev only after `develop` → `main`. *(Suspended by the develop-only rule above: until launch, dev deploys run from `develop`.)*

### Catalogue, Search, Offers and Shipping (Step 1b)

- **Catalogue tree**: `categories/{id}` (two levels, `ancestorIds`, `path`) and `brands/{id}` are public-read when `published == true` (queries must include `where('published', '==', true)`). Products carry `categoryId`, `categoryIds` (leaf plus ancestors), `brandId`, optional `gender` (`women` | `men` | `kids` | `unisex`; missing = not set, not lockable, not imported), `colors` (closed `ColorId` palette), `tags`, and derived `inStock`. `lockedFields` also accepts `colors` and `tags` (`inStock` is not lockable). `colors` is a list of palette ids (a product can have several, `multi` for 3+ colours); Check catalogue structure → Apply only fills `colors` when a product has none (from colour options, then the name); it never replaces or clears colours that are already set, locked or not. `functions/scripts/set-product-colors.mjs` (dry run by default, `--apply` to write) fills empty `colors` for the 37 products the backfill could not resolve and locks the field. Algolia mirrors `gender` as a faceted attribute (not `filterOnly`) so Shop can show the Gender filter with counts when data exists (rebuild search after deploy to refresh index settings). Seeds and helpers live in `catalog-taxonomy.ts` (functions and Angular copies, keep identical). `migrateCatalogStructure` (admin callable, passes `add` and `dropLegacy`) seeds categories, brands and `settings/shipping`, and backfills products; `onProductCountsChange` keeps counts current.
- **Product stock**: `stock`, `stockBySize`, and `inStock` are always written together by `stockFields()` / `bootstrapStock()` in `functions/src/products/stock.ts`. `stock` is a whole number ≥ 0 and the source of truth; `inStock` is always `stock > 0`. `stockBySize` is only on products with a `size` option, keyed by that option's value ids, and `stock` equals the sum of the map (Firestore rules cannot sum a map, so `validStock` only checks the integer, `inStock`, and a map of at most 20 entries). Bootstrap runs only when `stock` is not yet a number and never overwrites an existing `stock`: untracked products (`trackStock === false`) get `untrackedDefaultStock()` on every size, or that default as flat `stock` when there is no size option (`currentProjectId()` in `functions/src/project-id.ts` reads `GCLOUD_PROJECT`, then `projectID.value()` from `FIREBASE_CONFIG`, because 2nd-gen functions often leave `GCLOUD_PROJECT` unset; `atteya-store-dev` → 10, any other resolved id including prod `attiya-store` → 0; an empty id throws instead of writing 0); tracked products with variants sum `variants[].stock` per size id (sizes with no rows are 0), or sum every variant when there is no size option; tracked products with no variants have nothing to count from, so the migration leaves them without `stock` and reports them as `stockMissing` (the admin sets those counts by hand). `trackStock` and `variants[].stock` are no longer read for availability anywhere; only `bootstrapStock()` reads them, once, for a product that has no `stock` yet. Search, the product page, and checkout use `stock > 0` (and `stockBySize` per size) when `stock` is a number, otherwise the stored `inStock` flag (search and checkout treat a missing flag as out of stock). Search does not index `stock` or `stockBySize`. `ProductSchema` has no `trackStock` field and leaves `stock` and `stockBySize` optional with no default, so a product without a count falls back to `inStock`; a missing `inStock` still defaults to `true` in the browser. Do not run the catalogue migration on prod until that 0 default is accepted — it would hide every untracked product from search and listings. Do not recompute `inStock` in a trigger that writes the product doc. Admin stock edits go through the `setProductStock` callable (a transaction on the live doc that merges the changed sizes, recomputes `stock`/`inStock` with `stockFields()`, and writes `updatedBy` (uid) and `updatedAt`). There is no client write of stock fields and no stock log yet. The product form (`createProduct` / `updateProduct`) writes stock only on create and when the sizes change: kept sizes keep their counts, new sizes take the starting count, removed sizes are dropped, all through `stockFields()`. A size sent without an id counts as new even when that id matches an existing size, so its starting count is saved. Adding sizes to a product that had none replaces that total with the per-size starting counts.
